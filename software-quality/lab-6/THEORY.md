# Теория к ЛР6: метрики Чидамбера и Кемерера

Конспект по разделу 4.2 методички («Метрики Чидамбера и Кемерера»), написанный
так, чтобы можно было разобраться с нуля и ответить на защите. Примеры — на
программе из этой лабы (классы `Точка`, `Квадрат`, `Program`, см.
[`README.md`](./README.md)).

## 1. Зачем отдельные метрики для ООП

Метрики из прошлых лаб (Холстед, Джилб, Чепин, Маккейб) смотрят на программу как
на набор операторов и маршрутов. В объектно-ориентированной программе сложность
сидит ещё и в **структуре классов**: сколько у класса методов, насколько глубоко
он в иерархии наследования, со сколькими другими классами общается, насколько
его методы связаны общими данными. Операторы этого не видят: два класса могут
иметь одинаковое число строк, но один будет цельным, а другой — свалкой из
несвязанных методов, которую пора делить.

В 1994 г. Шьям Чидамбер и Крис Кемерер (Chidamber, Kemerer) предложили шесть
**проектных** метрик — их можно считать уже по диаграмме классов и заголовкам
методов, до того как написан весь код. Сокращённо набор называют **CK**.

| Метрика | Расшифровка | Что измеряет | Желательно |
| --- | --- | --- | --- |
| WMC | Weighted Methods per Class | сложность класса через сложность его методов | низкое |
| DIT | Depth of Inheritance Tree | глубина класса в иерархии наследования | умеренное (см. ниже) |
| NOC | Number Of Children | число непосредственных потомков | умеренное |
| CBO | Coupling Between Object classes | связанность класса с другими классами | низкое |
| RFC | Response For a Class | сколько методов может сработать в ответ на сообщение | низкое |
| LCOM | Lack of Cohesion Of Methods | насколько методы класса *не* связаны общими полями | низкое (лучше 0) |

Плюс вспомогательная **NM** (Number of Methods) — частный случай WMC.

DIT и NOC описывают **форму иерархии**, CBO и RFC — **внешние связи** класса
(CBO — статическую сторону, RFC — динамическую), WMC и LCOM — **внутреннее
устройство** класса.

## 2. Что в C# считать методом

Это надо решить до всякого подсчёта, иначе цифры «поплывут».

- **Конструкторы — методы.** В примере «Платёж за электроэнергию» у класса
  `Электро` методичка насчитала 4 метода, из них 2 конструктора. В нашей лабе
  конструкторы `Точка(...)` и `Квадрат(...)` тоже считаются.
- **Статические методы** (`Main`, `Запрос.Заполнить`) — методы, считаются.
- **Поля** — не методы. Они нужны для LCOM (какие методы к каким полям
  обращаются).
- **Свойства** (`public double A { get; set; }`) — спорный момент. Компилятор
  превращает свойство в методы `get_A`/`set_A`, поэтому многие инструменты
  считают каждый аксессор методом. Методичка про свойства не говорит; разумно
  либо считать каждый аксессор методом, либо не считать вовсе — и объяснить
  выбор. В нашей программе свойств нет, вопрос не возникает.
- **Унаследованные методы** — по выбору (см. NM). В примерах методички считаются
  только собственные.
- **Перегрузки** — разные методы (два конструктора `Электро` — два метода).
- **Методы, скрытые через `new`**, — собственный метод наследника. У `Квадрата`
  свой `Показать()`, а `Точка.Показать()` остаётся методом `Точки`.

## 3. WMC — взвешенные методы на класс

Пусть в классе n методов со сложностью c₁, …, cₙ. Тогда

**WMC = c₁ + c₂ + … + cₙ.**

Вес метода — любая метрика сложности: число строк, цикломатическое число
Маккейба, объём Холстеда. Её нормируют так, чтобы «обычный» метод имел сложность
около 1. Методичка в примерах берёт самый простой вариант — **число строк
метода** (от заголовка до закрывающей скобки включительно):

WMC(K) = L[0] + L[1] + … + L[n].

У нас: WMC (Квадрат) = 4 + 4 + 4 + 4 = 16, WMC (Program) = 24.

Почему WMC должна быть низкой:

- больше методов и сложнее методы — больше работы на реализацию и тестирование;
- все методы наследуются потомками, так что «толстый» базовый класс утяжеляет
  всю иерархию;
- класс с кучей методов, как правило, заточен под одно приложение, и повторно
  его использовать трудно.

Важно понимать, что **значение WMC зависит от выбранной меры**. Если взять
цикломатическую сложность, у нас WMC (Program) = 3 (одно `if` с `||`), а
WMC (Квадрат) = 4 — картина переворачивается. Сравнивать можно только значения,
посчитанные одним способом.

### NM — количество методов на класс

Если всем методам дать вес 1, WMC превращается в **NM** — просто число методов.
Её можно считать на ранних этапах, когда кода ещё нет, только список операций.

Два варианта учёта (методичка разрешает оба, но требует постоянства):

1. **Только собственные методы класса.** Унаследованные уже посчитаны там, где
   объявлены. Подход подчёркивает *инкрементность* класса — что он добавляет к
   родителю.
2. **Собственные + унаследованные.** Подчёркивает *пространство состояний* —
   всё, что умеет объект класса.

У нас по варианту 1: NM (Точка) = 2, NM (Квадрат) = 4, NM (Program) = 1. По
варианту 2 у `Квадрата` добавится `Точка.Показать()` — 5 (конструктор не
наследуется).

## 4. DIT — глубина дерева наследования

**DIT** класса — длина самого длинного пути от корня иерархии до этого класса,
то есть число классов-предков, которые могут на него влиять.

- `Точка` — корень, DIT = 0;
- `Квадрат : Точка` — DIT = 1.

Для программы в целом называют максимум (у нас DIT = 1, как и в примере 4.2.3).

**Про `System.Object`.** В C# любой класс неявно наследуется от `object`. Если
его считать, все значения DIT увеличатся на 1 (Точка — 1, Квадрат — 2).
Методичка его не учитывает; главное — делать одинаково для всех классов.

**Интерпретация — двоякая, и методичка это прямо говорит.** Большая глубина:

- плюс: выше абстракция, повторно используется больше кода, класс меньше
  насыщен собственными методами;
- минус: чтобы понять класс, надо прочитать всех предков; поведение сложнее
  предсказать; труднее тестировать.

Поэтому «чем больше, тем лучше» относится к абстракции, а на практике глубину
держат умеренной. Часто встречающийся ориентир — не больше 5–6 уровней.

При множественном наследовании (в C# — только интерфейсов) берут **самый
длинный** путь.

## 5. NOC — количество потомков

**NOC** — число **непосредственных** потомков класса (внуки не считаются).
У нас NOC (Точка) = 1, у остальных 0. В примере 4.2.3 у `Точки` NOC = 2
(`Окружность` и `Прямоугольник`).

- Больше NOC — больше повторного использования (наследование — одна из его
  форм).
- Но и риск: при большом числе детей родитель теряет абстракцию, часть детей
  может «не быть» родителем по смыслу (нарушение принципа подстановки).
- NOC показывает влияние класса на проект: изменение родителя затрагивает всех
  детей, и каждого надо перетестировать.

Методичка: хорошо спроектированная система — это скорее **лес** невысоких
деревьев, чем одно очень высокое дерево.

## 6. CBO — связанность между классами

**Определение.** CBO — число классов, с которыми связан данный класс. Класс A
связан с B, если A использует методы, поля или экземпляры B (вызывает метод,
создаёт объект, обращается к свойству). Второе определение из методички: CBO
равно количеству сцеплений класса, а **сцепление — это вызов метода или
свойства другого класса**.

**Как считает методичка в примерах.** Фактически — **число обращений** к
методам и свойствам других классов, а не число различных классов:

- `Запрос`: 8 вызовов `Console`, 2 — `int.Parse`, 2 — конструктора `Электро`,
  итого CBO = 12 (хотя различных классов три);
- `Program` в примере 4.2.3: 16 обращений.

Правила, которые из примеров следуют:

- вызов **своего** метода (`Сумма()` из `Инфо()`) в CBO не идёт;
- `int.Parse(Console.ReadLine())` — два обращения к двум классам;
- `new Электро(...)` — обращение к конструктору другого класса;
- `: base(x, y)` в примере 4.2.3 не учтён.

В лабе я считал так же, как в примерах (CBO (Program) = 21), и рядом привёл число
различных классов (CBO (Program) = 4). На защите лучше сразу сказать, что
определение говорит о классах, а примеры считают обращения, и что выбран вариант
примеров ради сопоставимости.

**Вопрос с наследованием.** У Чидамбера и Кемерера связь через наследование
формально тоже считается; многие инструменты её исключают (иначе каждый потомок
автоматически «связан» с родителем). Методичка `base(...)` не считает.

**Почему CBO должна быть низкой:** чем больше связей, тем сильнее изменения в
одном классе расходятся по другим, тем сложнее модифицировать и тестировать и
тем меньше шансов переиспользовать класс в другом приложении. Низкая
связанность — это модульность и инкапсуляция. Ориентир из литературы (для CBO
как числа классов) — не больше 5–6; для CBO как числа обращений общих порогов
нет.

## 7. RFC — отклик на класс

**RFC** — количество методов, которые могут быть выполнены в ответ на сообщение,
пришедшее объекту класса. Формула (4.2.3) методички:

**RFC = {R} + {M},**

где {M} — все методы класса, {R} — методы, которые вызываются из методов
класса. В исходном определении CK это **объединение множеств**
RS = M ∪ R₁ ∪ … ∪ Rₙ: каждый метод считается один раз, сколько бы раз его ни
вызвали, а вызовы своих методов уже сидят в M.

**Как считает методичка:** RFC = R + M, где M = NM, а R —

- в примере 4.2.3 просто равно CBO (число обращений к другим классам);
- в примере 4.2.2 у `Электро` R = 2: `string.Format` **и собственный
  `Сумма()`**.

У нас у `Квадрата` та же ситуация, что у `Электро` (`Показать()` вызывает
`Площадь()`), поэтому R = 2, RFC = 2 + 4 = 6. По «чистому» определению через
множество было бы 5. Для `Program`: R = 21 (все обращения), RFC = 22; через
множество различных методов — 10.

**Смысл.** RFC — мера потенциального взаимодействия класса, динамическая сторона
его внешних связей. Большой RFC — при одном вызове может сработать много кода,
значит, тестировщику надо понимать больше, тестовые последовательности длиннее,
отладка сложнее. «Самая плохая величина отклика» используется для оценки времени
тестирования. Часто встречающийся ориентир — RFC до 50.

Чем RFC отличается от CBO: CBO говорит, **с кем** класс связан, RFC — **сколько
методов** может быть задействовано. Класс может быть связан с одним классом, но
вызывать у него двадцать методов — CBO маленькая, RFC большая.

## 8. LCOM — отсутствие сцепления в методах

LCOM показывает, насколько методы класса **не** связаны между собой через общие
поля (переменные экземпляра). Если метрика высокая, класс, скорее всего,
собран из нескольких независимых частей, и его стоит разделить.

### Вариант методички (CK 1994, в литературе — LCOM2)

1. Для каждого метода выписать множество полей класса, к которым он обращается.
2. Перебрать все пары методов (их n·(n−1)/2).
3. P — число пар **без** общих полей, Q — число пар **с** общими полями.
4. **LCOM = P − Q, если P > Q, иначе 0.**

Наш `Квадрат`: 4 метода, 6 пар, все используют поле `a`. P = 0, Q = 6,
0 − 6 = −6 → LCOM = 0.

Класс с одним методом: пар нет, LCOM = 0 (`Program`). Класс без полей и с
несколькими методами: все пары без общих полей, LCOM = число пар (в примере
4.2.2 у `Запрос` два статических метода и нет полей → LCOM = 1 − 0 = 1).

Недостатки этого варианта, про которые могут спросить:

- из-за обрезания до нуля все «хорошие» классы неразличимы (все LCOM = 0);
- значение зависит от числа методов: у большого класса P − Q может быть большим
  даже при в целом разумном устройстве;
- конструкторы, геттеры и сеттеры сильно влияют: геттер трогает одно поле и
  почти ни с кем его не делит.

### Другие варианты (для кругозора)

- **LCOM (Henderson-Sellers, LCOM\*):** LCOM\* = (среднее по полям число
  методов, обращающихся к полю − m) / (1 − m), где m — число методов. Значение от
  0 (каждый метод трогает каждое поле) до 1 (каждое поле трогает один метод);
  больше 1 бывает, если есть поля, которые никто не использует. Нормирован и не
  зависит от размера класса.
- **LCOM4 (Hitz, Montazeri):** строится граф, где вершины — методы, ребро есть,
  если два метода используют общее поле или один вызывает другой. LCOM4 — число
  компонент связности. 1 — класс цельный; 2 и больше — класс можно разрезать на
  столько частей. Наглядный вариант: сразу видно, *как* делить класс.
- **LCOM1** (CK 1991) — просто число пар методов без общих полей (P, без вычитания
  Q); **LCOM3** (Li, Henry) — число компонент связности графа «методы — общие
  поля», то есть LCOM4 без учёта вызовов. На защите достаточно знать, что
  вариантов много и сравнивать можно только значения одной формулы.

В лабе используется вариант методички (P − Q с обрезанием до нуля).

**Что считать «полями класса» у наследника?** Наш `Квадрат.Показать()`
обращается к унаследованным `x`, `y`. Их можно считать переменными класса (они
доступны напрямую, `protected`), можно не считать. Для `Квадрата` разницы нет —
все методы и так делят поле `a`.

## 9. Как считать на практике (порядок работы)

1. Выписать листинг без комментариев и пустых строк, пронумеровать строки.
2. Для каждого класса перечислить методы (с конструкторами), их строки и число
   строк → **NM** и **WMC**.
3. Нарисовать иерархию наследования → **DIT** и **NOC**.
4. Пройти по каждому методу и выписать все вызовы чужих методов/свойств и
   создания объектов, с номерами строк → **CBO** (и различные классы для
   сравнения).
5. К этим вызовам добавить вызовы своих методов (если следуешь примеру 4.2.2)
   → R, **RFC = R + M**.
6. Для каждого метода — множество используемых полей; перебрать пары → P, Q,
   **LCOM**.
7. Свести в таблицу, сделать выводы: какой класс самый сложный, самый связанный,
   есть ли классы, которые стоит разделить.

## 10. Пороговые значения и интерпретация

Методичка конкретных порогов не даёт — только направления: WMC, CBO, RFC и
LCOM должны быть «разумно низкими», DIT — «возможно большим», но без перегиба в
непонятность. Ориентиры, которые часто приводят в литературе (они сильно
разнятся от источника к источнику, так что это именно ориентиры):

| Метрика | Тревожный признак |
| --- | --- |
| WMC (как число методов) | больше 20–50 |
| DIT | больше 5–6 |
| NOC | много детей у одного класса при низкой абстракции родителя |
| CBO (различных классов) | больше 5–14 |
| RFC | больше 50 (и особенно больше 100) |
| LCOM | > 0 — повод посмотреть на класс; LCOM4 ≥ 2 — класс можно разделить |

Наши значения далеко от всех порогов: классы маленькие, неглубокая иерархия,
LCOM = 0. Высокие CBO и RFC у `Program` — типичная картина для основного класса,
который только «дирижирует» остальными: в примерах методички у `Program` и
`Платежи` тоже максимальные значения.

## 11. Вопросы на защите

**Кто и когда предложил эти метрики, сколько их?**
Чидамбер и Кемерер, 1994 г., шесть метрик: WMC, DIT, NOC, CBO, RFC, LCOM. NM —
вспомогательная, частный случай WMC.

**Почему их называют проектными?**
Почти все можно посчитать по структуре классов (методы, наследование, связи)
ещё на этапе проектирования, до полного написания кода.

**Как считается WMC и от чего она зависит?**
Сумма сложностей методов класса. Зависит от выбранной меры сложности метода; в
методичке — число строк. У `Квадрата` 4 + 4 + 4 + 4 = 16.

**Чем NM отличается от WMC?**
NM — это WMC, где у каждого метода вес 1, то есть просто число методов.

**Учитываются ли унаследованные методы?**
Два варианта: только свои или свои плюс унаследованные. Оба допустимы, главное —
применять один вариант последовательно. В лабе — только свои, как в примерах.

**Считаются ли конструкторы методами?**
Да, в примерах методички конструкторы входят в число методов (у `Электро` два
конструктора из четырёх методов).

**Что такое DIT и какое значение хорошее?**
Длина пути от корня иерархии до класса. Большая глубина — больше абстракции и
повторного использования, но сложнее понимать и тестировать. У нас DIT = 1.

**Учитывается ли `System.Object`?**
В методичке нет. Если учитывать, все DIT увеличиваются на 1. Главное —
одинаково для всех классов.

**Чем NOC отличается от DIT?**
DIT — насколько класс глубоко (вверх по иерархии), NOC — сколько у класса
непосредственных детей (вниз на один уровень). Внуки в NOC не входят.

**Что такое CBO и почему её надо минимизировать?**
Число классов, с которыми связан данный (через вызовы методов, свойства,
создание объектов). Чем выше, тем сильнее изменения в одном месте расходятся по
программе, тем сложнее модификация, тестирование и повторное использование.

**Почему у вас CBO (Program) = 21, если классов всего четыре?**
Методичка в примерах считает обращения, а не классы (CBO (Запрос) = 12 при трёх
классах). Для сопоставимости посчитано так же; по числу различных классов
CBO (Program) = 4.

**Что такое RFC и чем она отличается от CBO?**
Число методов, которые могут выполниться в ответ на сообщение объекту:
собственные методы плюс вызываемые ими. CBO — с кем связан класс (статика),
RFC — сколько методов может сработать (динамика).

**Почему RFC (Квадрат) = 6, а не 5?**
По примеру 4.2.2 в R включается и вызов собственного метода (`Сумма()` у
`Электро`, `Площадь()` у нас). По исходному определению через множество
`Площадь()` уже есть в M и повторно не считается — было бы 5.

**Как считается LCOM в методичке?**
P — число пар методов без общих полей, Q — с общими. LCOM = P − Q, а при
отрицательном результате 0. У `Квадрата` 0 − 6 = −6 → 0.

**Что означает LCOM = 0? А большое значение?**
0 — методы связаны общими данными, класс цельный. Большое — методы работают с
разными полями, класс фактически состоит из нескольких, его стоит разделить.

**Какие ещё бывают варианты LCOM?**
LCOM* Хендерсона-Селлерса (нормирован от 0 до 1), LCOM4 Хитца и Монтазери (число
компонент связности графа методов). Значения разных вариантов между собой не
сравнивают.

**Почему у класса без полей LCOM не ноль?**
Если методов больше одного, ни одна пара не делит полей: P = число пар, Q = 0.
Так у `Запрос` в примере 4.2.2: LCOM = 1. Для чисто статических «сервисных»
классов это формальность, а не признак плохого дизайна.

**Какой класс в вашей программе самый сложный и почему?**
По WMC, CBO и RFC — `Program`: в `Main` весь ввод, проверка и вызовы остальных
классов. По NM — `Квадрат` (4 метода). Классы предметной области простые и
цельные (LCOM = 0).

**Что бы изменилось, если сделать `Показать()` виртуальным?**
На значения метрик — ничего: число методов, строк, вызовов и полей то же. Но
поведение изменится: в строке 56 при ссылке типа `Точка` вызвался бы
`Квадрат.Показать()` (позднее связывание), и вывод только угла стал бы невозможен
без отдельного метода.
