# Теория к ЛР8: метрики Абреу (MOOD)

Конспект по методичке (п. 4.4.1) с пояснениями, как всё это считать на C#.
Отчёт по самой лабе — в [README.md](README.md).

## 1. Откуда метрики и зачем

В 1994 году Фернандо Брито э Абреу (Fernando Brito e Abreu) предложил набор
метрик **MOOD** (Metrics for Object Oriented Design). В отличие от Холстеда
или Маккейба, которые смотрят на текст и управляющий граф, MOOD оценивает
**устройство классов**: что спрятано, что унаследовано, что переопределено и
кто кого вызывает.

Цели, которые ставил Абреу (по методичке):

- учесть базовые механизмы ООП — инкапсуляцию, наследование, полиморфизм и
  посылку сообщений;
- определить метрики формально, чтобы результат не зависел от того, кто
  считает;
- не зависеть от размера программы — поэтому все метрики это **доли** от 0
  до 1 (или проценты), а не абсолютные количества;
- не зависеть от языка — в определениях нет конструкций конкретного языка,
  только «видимый/скрытый», «унаследованный/переопределённый» и т. п.

Последний пункт на практике означает, что при переносе на конкретный язык
приходится договариваться, что считать скрытым, что методом и т. д. Для C#
такие договорённости разобраны ниже в п. 8.

## 2. Шесть метрик одной таблицей

| Метрика | Расшифровка | Механизм ООП | Что показывает | Хорошо, когда |
| --- | --- | --- | --- | --- |
| MHF | Method Hiding Factor — фактор закрытости метода | инкапсуляция | доля скрытых методов | выше (но не 100 %) |
| AHF | Attribute Hiding Factor — фактор закрытости свойства | инкапсуляция | доля скрытых полей | 100 % |
| MIF | Method Inheritance Factor — фактор наследования метода | наследование | доля унаследованных (и не переопределённых) методов среди доступных | умеренно; 70–80 % уже плохо |
| AIF | Attribute Inheritance Factor — фактор наследования свойства | наследование | доля унаследованных полей среди доступных | умеренно |
| POF (PF) | Polymorphism Factor — фактор полиморфизма | полиморфизм | сколько переопределений реально есть относительно максимально возможного | умеренно; > 10 % возможен обратный эффект |
| COF (CF) | Coupling Factor — фактор сцепления | посылка сообщений | доля реальных связей «клиент — поставщик» от всех возможных | как можно ниже |

Везде TC (total classes) — количество классов в программе. В моей лабе
TC = 4.

«Свойство» в методичке — это **поле** (атрибут) класса, а не C#-свойство
`{ get; set; }`. Дальше пишу «поле».

## 3. Инкапсуляция: MHF и AHF

### Обозначения

- M_v(C_i) — количество **видимых** методов класса C_i (интерфейс класса);
- M_h(C_i) — количество **скрытых** методов (реализация класса);
- M_d(C_i) = M_v(C_i) + M_h(C_i) — все методы, **определённые** в классе.
  Унаследованные сюда не входят.

Для полей то же самое: A_v, A_h, A_d = A_v + A_h.

### Упрощённая формула (именно ей пользуются примеры)

MHF = Σ M_h(C_i) / Σ M_d(C_i),  AHF = Σ A_h(C_i) / Σ A_d(C_i)

Суммы по всем TC классам. То есть: сколько методов (полей) во всей программе
скрыто, делённое на сколько их всего определено.

### Строгая формула

Абреу считает скрытость не «да/нет», а **долей классов, из которых член
не виден**. Для m-го метода i-го класса:

- is_visible(M_mi, C_j) = 1, если j ≠ i и класс C_j может вызвать M_mi,
  иначе 0 — (4.4.2);
- V(M_mi) = Σ_j is_visible(M_mi, C_j) / (TC − 1) — доля «других» классов,
  которые видят метод — (4.4.3);
- MHF = Σ_i Σ_m (1 − V(M_mi)) / Σ_i M_d(C_i) — (4.4.4).

Для полей — (4.4.6)–(4.4.8), точно так же.

Обе записи дают одно и то же, пока члены либо `public` (V = 1, скрытость 0),
либо `private` (V = 0, скрытость 1). Расходятся они на **`protected`**:
такой член виден из наследников, но не из остальных классов, V между 0 и 1.

В примере «Геометрия» методички поля `protected double x, y` класса Точка
названы закрытыми и посчитаны как A_h = 2, то есть по упрощённой формуле.
В отчёте я делаю так же, а строгое значение привожу рядом для сравнения:
в моей программе `U` и `faza` видны из двух наследников из трёх «чужих»
классов, V = 2/3, скрытость каждого поля 1/3, и
AHF = (1/3 + 1/3 + 2 + 3) / 7 = 17/21 ≈ 0,81 вместо 1.

### Как понимать

- **AHF** в идеале 100 %: все поля скрыты, с ними работают только методы
  своего класса. Открытое поле — это данные, которые кто угодно может
  испортить в обход проверок.
- **MHF**: по методичке, с ростом MHF уменьшается плотность дефектов и
  затраты на их исправление. Логика такая: класс обычно пишется пошагово,
  к публичному интерфейсу добавляются скрытые вспомогательные методы, и чем
  больше деталей спрятано, тем проще класс менять. Но 100 % недостижимо и не
  нужно — класс без открытых методов бесполезен. MHF = 0 в маленьких учебных
  программах (оба примера методички и моя лаба) — нормально: там просто нечего
  выносить в скрытые помощники.

## 4. Наследование: MIF и AIF

### Обозначения для методов класса C_i

- M_i(C_i) — **унаследованные и не переопределённые** (inherited);
- M_0(C_i) — **унаследованные и переопределённые** (overridden);
- M_n(C_i) — **новые**, то есть не унаследованные (new);
- M_d(C_i) = M_n + M_0 — определённые в самом классе (в тексте класса есть
  их тело);
- M_a(C_i) = M_d + M_i — **все доступные** в классе (available): свои плюс
  доставшиеся от предка без изменений.

Для полей — A_i, A_0, A_n, A_d = A_n + A_0, A_a = A_d + A_i.

### Формулы

MIF = Σ M_i(C_i) / Σ M_a(C_i) — (4.4.9)

AIF = Σ A_i(C_i) / Σ A_a(C_i) — (4.4.10)

Числитель — сколько всего по программе унаследовано «как есть», знаменатель —
сколько всего доступно (своё + унаследованное) во всех классах.

### Как понимать

- **MIF = 0** — эффективного наследования методов нет: либо наследования нет
  вообще, либо все унаследованные методы переопределены. У меня второй случай:
  у базового класса наследуется только `Печать()` (конструктор не
  наследуется), и оба наследника его переопределяют — этого требует условие.
- С ростом MIF плотность дефектов падает: готовый проверенный код не
  переписывается заново. Но при MIF порядка 70–80 % по методичке возможен
  обратный эффект — слишком глубокие и «толстые» иерархии трудно понимать.
  Вывод методички: умеренное наследование полезно.
- **AIF** — то же для полей. В моей лабе 4/11 ≈ 0,36: каждый наследник
  получает `U` и `faza` от базового класса.

### Что считается «переопределённым»

В методичке переопределением считается любое появление в наследнике метода с
тем же именем и сигнатурой. В примере «Геометрия» это `public new void
Показать()` — то есть **сокрытие** (`new`), а не `override`, и всё равно
M_0 = 1. В моей лабе — честный `override`. Для MOOD разницы нет, а для
программы есть (см. п. 8).

## 5. Полиморфизм: POF

### Обозначения

- M_0(C_i) — переопределённые методы класса;
- M_n(C_i) — новые методы класса;
- DC(C_i) — количество потомков класса (descendants count);
- M_d(C_i) = M_n + M_0.

### Формула

POF = Σ M_0(C_i) / Σ [M_n(C_i) · DC(C_i)] — (4.4.11)

**Числитель** — сколько переопределений реально есть, то есть сколько
существует «полиморфных ситуаций»: вызов метода может уйти в одну из
нескольких реализаций.

**Знаменатель** — сколько их могло бы быть максимум: каждый новый метод
каждого класса переопределён в каждом его потомке. Например, у моего
базового класса 2 новых метода и 2 потомка → максимум 4 переопределения.

В моей лабе POF = (0 + 1 + 1 + 0) / (2·2 + 0 + 0 + 0) = 2/4 = 0,5.
Половина знаменателя — конструктор базового класса, который в C#
переопределить нельзя. Методичка считает конструкторы методами, поэтому его
приходится учитывать; из-за этого POF у простых иерархий «базовый класс +
наследники с одним переопределением» почти всегда получается 0,5 (как в
примере «Геометрия»).

### Как понимать

Умеренный полиморфизм уменьшает плотность дефектов и затраты на доработку,
но по методичке при POF > 10 % возможен обратный эффект: чем больше
переопределений, тем труднее понять, какой код реально выполнится.

### Когда POF (и MIF, AIF) не считаются

Если наследования нет, знаменатель POF равен нулю (ни у кого нет потомков).
В примере «Платёж за электроэнергию» так и написано: «принцип наследования не
реализован, следовательно, расчёт метрики не имеет смысла» — это касается
MIF, AIF и POF. MHF, AHF и COF считаются всегда.

## 6. Посылка сообщений: COF

### Отношение «клиент — поставщик»

Класс C_c — **клиент** класса C_s (поставщика), если в C_c есть хотя бы одна
**неунаследованная** ссылка на поле или метод C_s:

is_client(C_c, C_s) = 1, если C_c → C_s и C_c ≠ C_s; иначе 0 — (4.4.12).

### Формула

COF = Σ_i Σ_j is_client(C_i, C_j) / (TC² − TC) — (4.4.13)

Знаменатель — максимально возможное число связей: каждый из TC классов может
быть клиентом каждого из остальных TC − 1, то есть TC·(TC − 1) = TC² − TC.
Связь класса с самим собой (рефлексивная) не считается.

### Что считать ссылкой

По примерам методички:

- **считается**: создание объекта (`new Электроустановка220(...)` — это вызов
  конструктора, то есть метода), вызов метода (`список[i].Печать()`), вызов
  статического метода (`Запрос.Заполнить(плэ)` в первом примере), обращение
  к полю другого класса;
- **не считается**: обращения наследника к членам предка — `base(x, y)`,
  `base.Печать()`, использование унаследованного поля. В примере «Геометрия»
  Окружность вызывает `base(x, y)` и печатает `x`, `y`, но
  is_client(Окружность, Точка) = 0. Сцепление — это связи, «не относящиеся к
  наследованию»;
- **не считаются** библиотечные классы (`Console`, `Math`, `string`): TC —
  это классы нашей программы, и связи ищутся только между ними.

Спорный момент — одно лишь упоминание типа, без вызова (например, параметр
`Электро[] платёж`). В моей программе этот вопрос не возникает: `Program`
ещё и вызывает `Печать()` через ссылку типа `СетевоеНапряжение`, так что
связь с базовым классом есть в любом случае.

### Как понимать

Сцепление плохо: чем больше классов зависят друг от друга, тем выше
плотность дефектов и затраты на доработку, хуже инкапсуляция и повторное
использование, труднее понимать и сопровождать. Надо добиваться, чтобы COF
был как можно меньше. Типичная картина для учебной программы: единственный
клиент — класс с `Main`, он использует все остальные классы, а классы
предметной области друг от друга не зависят,
COF = (TC − 1) / (TC² − TC) = 1 / TC. У меня 3/12 = 0,25.

## 7. Порядок расчёта (как в примерах)

1. Перечислить классы, TC.
2. MHF: для каждого класса выписать методы с модификаторами → M_h, M_d.
3. AHF: для каждого класса выписать поля → A_h, A_d.
4. MIF: для каждого класса M_i, M_0, M_n, M_d, M_a.
5. AIF: для каждого класса A_i, A_0, A_n, A_d, A_a.
6. POF: M_0, M_n, DC для каждого класса.
7. COF: для каждой пары (клиент, поставщик) is_client, с обоснованием по
   строкам программы.
8. Итоговая таблица и выводы по каждой метрике.

## 8. Как это ложится на C#

### Модификаторы доступа

| Модификатор | Кто видит | Как считать в MOOD |
| --- | --- | --- |
| `public` | все | видимый (V = 1) |
| `private` | только свой класс | скрытый (V = 0) |
| не указан (у члена класса) | то же, что `private` | скрытый — но см. про `Main` ниже |
| `protected` | свой класс и наследники | по примерам методички — скрытый; строго V = (число наследников) / (TC − 1) |
| `internal` | вся сборка | в однофайловой программе все классы в одной сборке, значит фактически видимый |
| `protected internal` | наследники **или** вся сборка | видимый (по тем же причинам) |
| `private protected` | наследники **в той же сборке** | как `protected` |

Про `Main`. В C# метод без модификатора — `private`, но в обоих примерах
методички `static void Main(...)` назван «по умолчанию открытым» и посчитан
как M_h = 0. Чтобы не спорить с методичкой и не писать заведомо неточную
фразу, я объявил его явно `public static void Main()`: тогда он открыт и по
языку, и по отчёту, а значения метрик совпадают с тем, как считает
методичка.

### Что считать методом

По примерам — всё, что имеет тело и вызывается: обычные методы, статические
методы, **конструкторы**. Конструкторы в C# не наследуются, поэтому в M_i
наследника они не попадают, а в M_n своего класса — попадают. Свойства
`{ get; set; }` в методичке не встречаются; если бы были, логично считать
их аксессоры методами (в IL это методы `get_X`/`set_X`).

### Что считать полем

Поля класса, в том числе `static` (в первом примере `private static double
тариф` посчитан как поле). Локальные переменные методов — **не поля**:
`список`, `n`, `вид` в моём `Main` в AHF не входят.

### `virtual` / `override` / `new`

- `virtual` в базовом классе разрешает переопределение;
- `override` в наследнике переопределяет, вызов по ссылке базового типа
  уходит в метод реального объекта (позднее связывание) — это настоящий
  полиморфизм;
- `new` в наследнике **скрывает** метод предка: какой метод вызовется,
  решает тип ссылки, а не объекта (раннее связывание). Поэтому в примере
  «Геометрия» вызов по массиву `Точка[]` всегда печатал «Точка», и
  приходилось делать приведения типов.

Для MOOD `override` и `new` одинаковы — оба дают M_0 = 1. Моё условие
требует именно виртуальный метод печати, поэтому `virtual`/`override`, и
вывод идёт одним циклом без приведений типов.

### Наследование полей

Наследник получает все поля предка, но **доступны** ему только `public`,
`protected`, `internal`. `private`-поле физически есть в объекте, но
наследник к нему обратиться не может. В MOOD A_i — это «унаследованные
доступные» поля, поэтому поля базового класса я сделал `protected`: они
нужны наследникам для расчёта тока. Если бы они были `private`, AIF был бы 0,
а наследникам пришлось бы получать `U` через дополнительный открытый метод.

| --- | :---: | :---: | :---: | :---: | :---: |
| СетевоеНапряжение | 2 (ctor, `Печать` virtual) | 2 protected | 0 / 0 / 2 | 0 / 2 | 2 |
| Электроустановка220 | 2 (ctor, `Печать` override) | 2 private | 0 / 1 / 1 | 2 / 2 | 0 |
| Электроустановка360 | 2 (ctor, `Печать` override) | 3 private | 0 / 1 / 1 | 2 / 3 | 0 |

MHF = 0/7 = 0; AHF = 7/7 = 1 (строго 17/21 ≈ 0,81); MIF = 0/7 = 0;

## 10. Вопросы на защите

**Что такое MOOD и чем эти метрики отличаются от Холстеда и Маккейба?**
Набор метрик Абреу для объектно-ориентированных программ. Холстед считает
операторы и операнды, Маккейб — ветвления в графе управления, то есть оба
смотрят «внутрь» методов. MOOD смотрит на уровень классов: инкапсуляцию,
наследование, полиморфизм и связи между классами. Все метрики — доли от 0 до 1,
поэтому не зависят от размера программы.

**Какие метрики к какому механизму ООП относятся?**
Инкапсуляция — MHF, AHF; наследование — MIF, AIF; полиморфизм — POF;
посылка сообщений — COF.

**Почему MHF у вас 0? Это плохо?**
Все методы — конструкторы, `Печать()` и `Main` — это интерфейс классов, их
вызывают снаружи. Скрытых вспомогательных методов в такой маленькой задаче
нет: расчёт тока и сопротивления — одна строка. В обоих примерах методички
MHF тоже 0. Для больших классов низкий MHF был бы тревожным знаком.

**Почему `protected`-поля посчитаны закрытыми? Их же видят наследники.**
Так сделано в примере «Геометрия» (поля `x`, `y` класса Точка), я следую
образцу. Строго по формуле (4.4.8) `protected`-поле видно из двух классов из
трёх, его закрытость 1/3, и AHF получается 17/21 ≈ 0,81. Это значение я тоже
привёл в отчёте.

**Чем M_i отличается от M_0, а M_d от M_a?**
M_i — унаследовано и не тронуто, M_0 — унаследовано и переопределено. M_d —
то, что написано в самом классе (новые + переопределённые), M_a — всё, что
в классе можно вызвать (M_d плюс унаследованное без изменений).

**Почему у наследников M_i = 0, они же наследуют от базового класса?**
У базового класса два метода: конструктор и `Печать()`. Конструкторы в C#
не наследуются, а `Печать()` в обоих наследниках переопределён.
Непереопределённых унаследованных методов не остаётся.

**Что значит MIF = 0?**
По методичке — отсутствие эффективного наследования методов: например, все
унаследованные методы переопределены. У меня именно так, и это требование
задачи. При этом код базового метода реально используется через
`base.Печать()`, но формула этого не видит.

**Как считается знаменатель POF и что он означает?**
Σ M_n · DC — максимальное число полиморфных ситуаций, если бы каждый новый
метод каждого класса был переопределён во всех потомках. У меня 2 новых
метода базового класса × 2 потомка = 4.

**POF = 50 % — это много?**
По методичке при POF > 10 % возможен обратный эффект — рост дефектов и
затрат. Но здесь 50 % — следствие условия (виртуальная печать с
переопределением в каждом наследнике) и того, что конструктор базового
класса тоже считается методом, хотя переопределить его нельзя. Весь
возможный в задаче полиморфизм использован.

**Чем `override` отличается от `new`? Как это влияет на метрики?**
`override` — позднее связывание: метод выбирается по реальному типу объекта.
`new` — сокрытие: метод выбирается по типу ссылки. В примере «Геометрия»
использован `new`, поэтому цикл по массиву `Точка[]` печатал только
«Точка». На метрики не влияет: в обоих случаях метод считается
переопределённым (M_0).

**Почему наследники не являются клиентами базового класса, они же
вызывают `base(...)` и используют `U`?**
Клиентская связь по определению требует **неунаследованной** ссылки.
Обращения к членам предка — это наследование, а COF считает только
сцепление, не относящееся к наследованию. Так же в примере: is_client
(Окружность, Точка) = 0.

**Почему `Program` — клиент `СетевоеНапряжение`, если он создаёт только
наследников?**
`Program` вызывает метод `Печать()` класса `СетевоеНапряжение` через ссылку
базового типа (строка 77) и держит массив этого типа (строка 57). То, что
на деле выполнится переопределённый метод, — уже полиморфизм; сам вызов
адресован базовому классу.

**Откуда TC² − TC?**
Каждый из TC классов может быть клиентом каждого из остальных TC − 1:
TC · (TC − 1). Отношение класса с самим собой не считается.

**Что будет с COF, если добавить класс?**
Если новый класс ни с кем не связан, знаменатель вырастет (для 5 классов —
20), а числитель нет, COF упадёт до 3/20 = 0,15. Если `Program` начнёт его
использовать — 4/20 = 0,2. В общем случае, когда `Program` — клиент всех
остальных классов, а других связей нет, COF = 1 / TC.

**Как повысить AIF или MIF в вашей программе?**
AIF — вынести общее поле `type` из наследников в базовый класс: тогда
у базового класса станет 3 поля, у наследников — по три унаследованных и
по одному-два своих, AIF = (0 + 3 + 3 + 0) / (3 + 4 + 5 + 0) = 6/12 = 0,5.
Но условие задачи явно кладёт *type* в производные объекты, поэтому я так
не делал. MIF поднять нельзя, не нарушив условия:
для этого наследники должны пользоваться `Печать()` базового класса без
переопределения.

**Почему в примере «Платёж за электроэнергию» MIF, AIF и POF не считались?**
Там нет наследования: у классов нет ни предков, ни потомков. Знаменатель
POF (Σ M_n · DC) равен нулю, а MIF и AIF были бы тождественно нулевыми, не
неся никакой информации. Методичка пишет «расчёт не имеет смысла».

**Почему метрики у вас почти совпали с примером «Геометрия»?**
Структура та же: базовый класс с конструктором и методом вывода, два
наследника с конструктором и переопределённым методом, класс `Program`,
использующий все три. Метрики Абреу описывают именно структуру, предметная
область на них не влияет. Отличается только AIF (4/11 против 4/9) — у моих
наследников на одно собственное поле больше.
