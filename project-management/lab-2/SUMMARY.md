# Работа 2. Описание содержания проекта — коротко

Шпаргалка к показу преподавателю. Документ — [01-scope-statement.docx](01-scope-statement.docx),
задание — [README.md](README.md).

## Суть

Устав говорит, *зачем* проект и в каких рамках. Описание содержания говорит, *что именно*
делаем: все работы, которые нужны, и только их. Содержание проекта — это работы, содержание
продукта — свойства и функции результата. Документ нужен, чтобы в конце Заказчик принял
работу по заранее записанным критериям, а лишние запросы можно было отсечь словами
«это вне границ проекта». Из задач этого документа потом строится ИСР.

## Что в документе

| Раздел | Что у нас |
| --- | --- |
| Цель | из Устава: до 31.03.2027 приложение iOS/Android в эксплуатации, публикация до 15.01.2027 |
| Критерии | срок, бюджет ≤ 10 000 000 руб., содержание = задачи раздела 5, качество = протокол испытаний |
| Задачи и результаты | 7 задач по порядку выполнения, у каждой результат-существительное |
| Границы | входит приложение, сервер, интеграции, обучение, поддержка; не входит веб-версия и код систем заказчика |
| Приёмка | Заказчик Василенко И., демонстрация и испытания, протокол |
| Ограничения / допущения | 5 / 4 с авторами, у допущений — последствие невыполнения |

## Откуда что взято

- Цель, ограничения и допущения — из Устава (методичка: «переносится из Устава»).
- Задачи — это 6 пунктов концепции Устава, разбитые подробнее; седьмая задача отделяет
  испытания от публикации.
- Последствия допущений привязаны к критериям успеха: срыв доступа к тестовой среде бьёт
  по сроку, изменение интерфейсов Заказчика — по бюджету и сроку.

## Как рассказывать

> Описание содержания мы сделали по шаблону на основе Устава. Цель перенесена без изменений,
> критерии достижения — по четырём критериям успеха: срок, бюджет, содержание и качество.
> Шесть пунктов концепции Устава разбиты на семь задач, у каждой есть результат: от
> согласованных требований до опубликованного приложения и обученных операторов. В границах
> явно сказано, что веб-версия и доработка систем Заказчика в проект не входят. Принимает
> результат Заказчик по протоколу испытаний. Ограничения и допущения взяты из Устава,
> для каждого допущения указано, на какой критерий повлияет его невыполнение.

## Возможные вопросы

1. **Чем содержание проекта отличается от содержания продукта?** Проект — это работы,
   продукт — функции и свойства результата (заказ, оплата, баллы, уведомления).
2. **Зачем границы, если есть задачи?** Чтобы явно записать, чего *не* делаем (веб-версия),
   и не забыть то, что делать надо (обучение операторов, поддержку).
3. **Что будет, если не выполнится допущение?** Для каждого написано: задержка интеграции
   и испытаний, рост бюджета или задержка публикации.
4. **Почему дата утверждения позже Устава?** Описание опирается на утверждённый Устав,
   поэтому утверждается после него, а согласование — раньше утверждения.
5. **Кто разрабатывает документ?** Руководитель проекта с командой, он же его утверждает
   и отвечает за актуальность.
6. **Как используются задачи дальше?** Из них строится иерархическая структура работ (ИСР).
