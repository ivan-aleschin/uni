# ЛР№3 «Регистровый файл и память инструкций» — формулировка задания

> Оригинальная методичка: https://github.com/MPSU/APS/tree/master/Labs/03.%20Register%20file%20and%20memory

## Цель

Описать на языке SystemVerilog элементы памяти для будущего процессора:

- память инструкций (ROM, асинхронное чтение);
- регистровый файл (3 порта: 2 на чтение асинхронно + 1 на запись синхронно).

## Что нужно сделать

### 1. Память инструкций `instr_mem`

Прототип (предоставлен методичкой в готовом виде, не правится):

```systemverilog
module instr_mem
  import memory_pkg::INSTR_MEM_SIZE_BYTES;
  import memory_pkg::INSTR_MEM_SIZE_WORDS;
(
  input  logic [31:0] read_addr_i,
  output logic [31:0] read_data_o
);
```

Требования:

- 32-битные ячейки, `INSTR_MEM_SIZE_WORDS` штук (= `INSTR_MEM_SIZE_BYTES / 4 = 128`);
- инициализация содержимым файла `program.mem` через `$readmemh`;
- асинхронное чтение (через `assign`, без регистра на выходе);
- адресация **побайтовая** (как в RISC-V), но в массиве — по словам, поэтому два младших бита `read_addr_i` отбрасываются;
- старшие биты адреса вне диапазона памяти тоже отбрасываются (см. срез `[$clog2(INSTR_MEM_SIZE_BYTES)-1:2]`).

### 2. Регистровый файл `register_file`

Прототип:

```systemverilog
module register_file (
  input  logic        clk_i,
  input  logic        write_enable_i,
  input  logic [ 4:0] write_addr_i,
  input  logic [ 4:0] read_addr1_i,
  input  logic [ 4:0] read_addr2_i,
  input  logic [31:0] write_data_i,
  output logic [31:0] read_data1_o,
  output logic [31:0] read_data2_o
);
```

Требования:

- внутренний массив **должен называться `rf_mem`** (требование верификационного окружения, оно лезет в `DUT.rf_mem` напрямую);
- размер `rf_mem[0:31]` — ровно 32 регистра по 32 бита (тест проверяет: попытка записать в `rf_mem[32]` не должна получиться);
- **2 асинхронных порта чтения** (без регистров перед выходом, через `assign`);
- **1 синхронный порт записи** (`always_ff @(posedge clk_i)` + проверка `write_enable_i`);
- **регистр `x0` — аппаратный ноль** [RISC-V spec, стр. 21]:
  - чтение по адресу `0` всегда возвращает `32'd0` (любое состояние ячейки);
  - запись по адресу `0` игнорируется.

Реализовать «аппаратный ноль» допустимо одним из двух способов:

1. **Мультиплексор перед выходом**: `assign rdN = (raN == 0) ? 0 : rf_mem[raN];`
2. Инициализация `rf_mem[0] = 0` + запрет записи по адресу 0.

Я выбрал первый — он более явный и не зависит от поведения симулятора в отношении неинициализированной памяти.

## Файлы лабораторной работы

| Файл | Назначение |
|---|---|
| `memory_pkg.sv` | пакет с константами размеров памяти (`INSTR_MEM_SIZE_BYTES`, `DATA_MEM_SIZE_BYTES`) |
| `design.sv` | мои реализации `instr_mem` и `register_file` |
| `lab_03.tb_register_file.sv` | официальный тестбенч (с reference-моделью `register_file_ref`, имена которой обфусцированы) |
| `program.mem` | (опционально) данные для инициализации `instr_mem` при моделировании |

## Проверка

Тестбенч `lab_03.tb_register_file.sv` сравнивает мой `register_file` с reference-моделью `register_file_ref`. Сценарии:

1. Проверка отсутствия инициализации (после reset чтение по адресу `1` должно дать `x`).
2. Проверка границы памяти (`rf_mem[32]` не должен существовать).
3. Проверка чтения `x0`.
4. Проверка запрета записи в `x0`.
5. 31 запись случайных значений с `we = $urandom % 2` → чтение и сравнение всех 32 регистров с reference-моделью.
6. Финальная проверка «свежезаписанных» данных.

Ожидаемый результат: `Number of errors: 0`.

## Проверка в ПЛИС (Nexys A7-100T)

Методичка требует проверить регистровый файл на отладочном стенде (см. `board files/` в оригинальном репозитории). Эта часть выполняется в Vivado, средствами тулчейна — переключатели `sw_i` и светодиоды `led_o` подключаются к портам RF через wrapper из `board files`.

В моей сдаче эта часть выполняется уже на этапе ЛР4 (CYBERcobra) и далее — модуль `register_file` будет напрямую использоваться внутри `cybercobra.sv` и в `processor_core` всех последующих лаб.
