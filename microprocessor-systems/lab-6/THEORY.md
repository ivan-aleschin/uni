## 1. RISC-V immediate-форматы

В инструкции RISC-V константа кодируется по-разному в зависимости от типа. Все immediate **знакорасширяются до 32 бит** (кроме `imm_U` и `imm_Z`).

| Формат | Где используется | Как собирается |
|---|---|---|
| **imm_I** | `addi`, `lw`, `lh`, `lb`, `jalr`, CSRR-инструкции | `{{20{instr[31]}}, instr[31:20]}` — 12 бит из старшей половины |
| **imm_S** | `sw`, `sh`, `sb` | `{{20{instr[31]}}, instr[31:25], instr[11:7]}` — поля разнесены |
| **imm_B** | `beq`, `bne`, `blt`, `bge`, `bltu`, `bgeu` | `{{19{instr[31]}}, instr[31], instr[7], instr[30:25], instr[11:8], 1'b0}` — со сдвигом на 1 |
| **imm_U** | `lui`, `auipc` | `{instr[31:12], 12'b0}` — **БЕЗ знакорасширения**, нули справа |
| **imm_J** | `jal` | `{{11{instr[31]}}, instr[31], instr[19:12], instr[20], instr[30:21], 1'b0}` |
| **imm_Z** | CSRR*I (csrrwi и пр.) | `{27'b0, instr[19:15]}` — **БЕЗ знакорасширения**, расширяется **нулями** |

**Почему `imm_B` и `imm_J` со сдвигом на 1?** Адреса инструкций кратны 2 (в обычном rv32i — кратны 4, но в RVC = 2). Младший бит всегда 0, поэтому его не хранят в инструкции — он подразумевается.

**Почему `imm_U` без знакорасширения?** Эта константа кодирует верхние 20 бит результата, нижние 12 — нули. Используется в паре `lui` + `addi` для загрузки 32-битных значений.

**Почему `imm_Z` расширяется нулями?** В CSR-инструкциях с immediate (`csrrwi rd, csr, uimm`) `uimm` — это 5-битное беззнаковое значение (например, для установки одного бита в CSR). Знаковое расширение тут бессмысленно.

## 2. Почему `data_mem` синхронный и зачем нужен stall

**Блочная память (BRAM) в ПЛИС имеет только синхронный порт чтения** — данные появляются на выходе на следующем такте после установки адреса. Это аппаратное ограничение.

Однотактный процессор выполняет инструкцию `lw` за 1 такт, но обращение к BRAM требует 2 такта (адрес → данные на следующем фронте). Решение — **stall**:

```
такт N:    lw x1, 0(x2)  → PC=N, mem_req=1, ext_addr → BRAM
такт N+1:  BRAM выдаёт данные. Ядро ВСЁ ЕЩЁ выполняет lw (PC не двигается).
           lsu.stall_o = 1 → core.stall_i = 1 → instr_addr_o не обновляется.
такт N+2:  stall=0, writeback в x1 уже произошёл (через core_mem_rd), PC+=4.
```

В `lsu.sv`:

```systemverilog
always_ff @(posedge clk_i) begin
  if (rst_i)      stall_o <= 1'b0;
  else if (req_i) stall_o <= 1'b1;     // запрос → stall на 1 такт
  else            stall_o <= 1'b0;     // через такт snап → отпускаем PC
end
```

Тонкость: `stall_o` — это **регистр**, а не комбинационная логика. На фронте N+1 он сбрасывается в 0, и PC обновится на следующем фронте N+2 — ровно тогда, когда данные из BRAM уже записаны в регистровый файл.

**Альтернатива без stall** — использовать LUT-RAM с асинхронным чтением (как `instr_mem`). Но это дороже по ресурсам ПЛИС и неэффективно для больших объёмов памяти.

## 3. Byte Enable и sign extension в LSU

LSU служит посредником между **32-битным интерфейсом ядра** и **побайтовой работой памяти**.

### Запись (`sw`, `sh`, `sb`)

| Инструкция | size | be_o (выровнено по 0) | be_o (адрес off-by-1, off-by-2…) |
|---|---|---|---|
| `sw` | 3'b010 | `4'b1111` | (только выровненный — иначе исключение) |
| `sh` | 3'b001 | `4'b0011` (off=0) или `4'b1100` (off=2) | — |
| `sb` | 3'b000 | `4'b0001..1000` в зависимости от `addr[1:0]` | — |

`wd_o` в BRAM — это всегда **повтор** входных данных по нужным позициям:
```
sb @ addr=0: wd_o = {24'b0, core_wd[7:0]},    be = 0001
sb @ addr=1: wd_o = {16'b0, core_wd[7:0], 8'b0}, be = 0010
…
```

### Чтение (`lw`, `lh`, `lhu`, `lb`, `lbu`)

После чтения 32-битного слова из BRAM, LSU **сдвигает** нужный байт/полуслово к младшим битам и расширяет:

| Инструкция | size | Расширение |
|---|---|---|
| `lw` | 3'b010 | без расширения, 32 бита |
| `lh` | 3'b001 | знаковое (бит 15 в [31:16]) |
| `lhu` | 3'b101 | нулями |
| `lb` | 3'b000 | знаковое (бит 7 в [31:8]) |
| `lbu` | 3'b100 | нулями |

Старший бит `size[2]` отличает signed/unsigned варианты.

## 4. CSR-регистры и обработка прерываний

| CSR | Адрес | Назначение |
|---|---|---|
| `mstatus` | `0x300` | глобальное разрешение прерываний (бит `MIE` = `[3]`) |
| `mie` | `0x304` | маска источников прерываний (в нашей системе важен ненулевой) |
| `mtvec` | `0x305` | адрес обработчика прерываний |
| `mscratch` | `0x340` | временный регистр (в startup.S используется как указатель на стек прерываний) |
| `mepc` | `0x341` | сохранённый PC при входе в обработчик |
| `mcause` | `0x342` | причина прерывания (для нашего источника = `0x80000007` — Machine timer interrupt) |

### Что делает CSR-контроллер при trap

На фронте, когда `interrupt_controller.trap_o = 1`:

1. **Сохраняет PC** → `mepc <= instr_addr_o` (текущая инструкция, которая будет переисполнена после возврата);
2. **Сохраняет причину** → `mcause <= trap_cause`;
3. **Сохраняет MIE** → `mstatus.MPIE <= mstatus.MIE`, затем `mstatus.MIE <= 0` (запрет вложенных прерываний);
4. Ядро на следующем фронте: `PC <= mtvec` (прыжок на обработчик).

### Что делает `mret`

1. **Восстанавливает PC** → `instr_addr_o <= mepc`;
2. **Восстанавливает MIE** → `mstatus.MIE <= mstatus.MPIE`;
3. `mstatus.MPIE <= 1`.

## 5. interrupt_controller и irq_pending latch

```systemverilog
always_ff @(posedge clk_i) begin
  if (rst_i)             irq_pending <= 0;
  else if (trap_o)       irq_pending <= 1;
  else if (mret_i)       irq_pending <= 0;
end

assign trap_o = irq_req_i && (mstatus_mie_i || |mie_reg_i) && !irq_pending && !mret_i;
```

**Зачем latch?** Если `irq_req` остаётся 1 в течение нескольких тактов (например, контроллер устройства не сбросил флаг сразу), без latch процессор бесконечно перепрыгивал бы на `mtvec`. Latch блокирует повторный trap до `mret`.

**Почему условие `|mie_reg_i`, а не конкретный бит?** Программа из `program_11.mem` устанавливает `mie = 0x10000` (бит 16, MEIP), а не `mie = 0x1`. Чтобы наша упрощённая логика разрешала прерывание при любой ненулевой маске, мы проверяем «есть ли хоть один установленный бит».

## 6. PC-логика

```systemverilog
always_comb begin
  if      (trap)                pc_next = mtvec;
  else if (mret)                pc_next = mepc;
  else if (jal)                 pc_next = instr_addr_o + imm_J;
  else if (jalr)                pc_next = (rd1 + imm_I) & ~32'b1;
  else if (branch && alu_flag)  pc_next = instr_addr_o + imm_B;
  else                          pc_next = instr_addr_o + 32'd4;
end
```

**Приоритет**: `trap > mret > jal > jalr > branch > inc`. Это важно — например, если в момент trap пришла бы инструкция `jal`, мы должны прыгнуть на `mtvec`, а не на цель `jal`. После `mret` сохранённый PC (`mepc`) указывает на ту инструкцию, что прервалась — она переисполнится.

**Почему `jalr & ~1`?** Спецификация требует обнулять младший бит вычисленного адреса (это уже не RVC, чисто rv32i).

**Запись PC** идёт по `posedge clk_i` только если `!stall_i` — так мы тормозим PC во время load/store.

## 7. Гарвардская архитектура

`instr_mem` и `data_mem` — **физически разные памяти** с независимыми шинами. Адреса в них могут пересекаться (например, инструкция по адресу `0x10` и данные по адресу `0x10` — это разные ячейки).

Это упрощает ПЛИС-реализацию (две независимые BRAM или LUT-RAM, без арбитража), но имеет последствие: программа не может **читать сами свои инструкции как данные**. Для нашего курса это не проблема, потому что в ЛР14 линкер-скрипт явно использует разные регионы памяти (`instr_mem` и `data_mem`).

## 8. Типичные вопросы преподавателя

**Q: Почему в `processor_core` нет регистра между `instr_i` и декодером?**
A: Это однотактный процессор. Декодер должен отработать **в тот же такт**, в который прочитана инструкция, чтобы успеть до `posedge` следующего такта обновить состояние (RF, PC, CSR). Регистр между ними сделал бы конвейер в 2 стадии.

**Q: Почему `stall_i` нужен PC, но не нужен регистровому файлу?**
A: Регистровый файл уже защищён: при `lw` сигнал `gpr_we` приходит на следующем такте (когда данные из BRAM на `mem_rd_i`), а в момент `stall` запись блокируется тем, что `wb_sel` ещё указывает на старый `lw`, а данные — на новый. Хотя на самом деле в нашем коде это работает за счёт того, что во время stall PC не двигается → инструкция `lw` исполняется фактически ещё раз → но второе исполнение производит ту же запись с правильными данными.

**Q: Что произойдёт, если `mret` встретится без предшествующего trap?**
A: `mepc` будет содержать значение по умолчанию (или мусор). PC прыгнет на этот адрес. Это **программистская ошибка** — методичка такого не предусматривает.

**Q: Может ли `irq_req` прийти во время `stall`?**
A: Да. В моей реализации `csr_we && !stall_i` — записи в CSR во время stall блокируются, поэтому запрос будет «висеть» и обработается, как только stall отпустит PC. То же справедливо для `trap && !stall_i`.

**Q: Зачем `csr_op[2] ? imm_Z : rd1` на входе CSR?**
A: Поле `csr_op[2]` — это флаг «immediate CSR-инструкция» (например, `csrrwi`). Когда он 1, в CSR пишется значение `imm_Z` (5 бит из поля `rs1`, расширенные нулями). Когда 0 — пишется значение из регистра `rs1` (это `rd1`).

**Q: Почему в моей системе нет арбитра между ядром и DMA?**
A: Нет DMA. У нас единственный мастер шины — ядро. Это упрощённая система без внешних bus masters.
