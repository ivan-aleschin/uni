## 1. Соглашение о вызовах (calling convention) RISC-V

В отличие от ваших программ на ассемблере в ЛР4, компилятор C **не может пользоваться всеми 32 регистрами произвольно**. Нужно общее соглашение, чтобы вызов функции не разрушал данные вызывающей.

| Регистр | ABI name | Назначение | Кто сохраняет |
|---|---|---|---|
| `x0` | `zero` | hard-wired 0 | — |
| `x1` | `ra` | return address | **Caller** |
| `x2` | `sp` | stack pointer | **Callee** |
| `x3` | `gp` | global pointer | — (не меняется) |
| `x4` | `tp` | thread pointer | — (не меняется) |
| `x5–7` | `t0–t2` | temporaries | **Caller** |
| `x8` | `s0/fp` | saved / frame pointer | **Callee** |
| `x9` | `s1` | saved | **Callee** |
| `x10–11` | `a0–a1` | args / return values | **Caller** |
| `x12–17` | `a2–a7` | args | **Caller** |
| `x18–27` | `s2–s11` | saved | **Callee** |
| `x28–31` | `t3–t6` | temporaries | **Caller** |

**Caller-saved** (= Caller обязан сохранить, если они ему нужны после вызова): функция может изменить эти регистры без предупреждения. Если в `a0` лежит важное значение и я хочу его сохранить после вызова `foo()`, я **сам** должен записать `a0` на стек **до** `call foo` и восстановить **после**.

**Callee-saved**: функция, которая хочет использовать эти регистры, обязана сохранить их на стек **в начале** своего тела и восстановить **в конце**, перед `ret`. Это позволяет вызывающему рассчитывать, что после возврата `s0..s11` остались такими же.

**Пример**: GCC скомпилирует `int_handler` примерно так:

```assembly
int_handler:
    addi sp, sp, -16          ; рамка стека
    sw   ra, 12(sp)           ; сохраняем ra (caller-saved, но мы вызываем внутри)
    sw   s0, 8(sp)            ; сохраняем s0 (мы его будем использовать)
    addi s0, sp, 16           ; frame pointer
    ...тело int_handler...
    lw   s0, 8(sp)            ; восстанавливаем
    lw   ra, 12(sp)
    addi sp, sp, 16
    ret
```

## 2. Linker script (`linker_script.ld`)

Линкер собирает объектные файлы (`startup.o`, `main.o`) в один ELF-файл. Он решает:

- **где** в памяти лежит каждая секция (`.text`, `.data`, `.bss`, `.stack`);
- **как** разрешать ссылки между файлами (например, `call main` в `startup.S` → адрес функции `main` в `main.o`);
- **какие** глобальные переменные доступны для startup (например, `_bss_start`, `_stack_ptr`, `_gbl_ptr`).

### Регионы памяти

```ld
MEMORY {
  instr_mem (x)  : ORIGIN = 0x00000000, LENGTH = 1K
  data_mem  (!x) : ORIGIN = 0x00000000, LENGTH = 2K
}
```

- `(x)` = executable, `(!x)` = non-executable.
- Обе памяти начинаются с `0x00000000` — это **гарвардская архитектура**: адресные пространства физически разные.

### VMA vs LMA (виртуальный адрес vs адрес загрузки)

Линкеру **не нравится** размещать две разные секции по одному адресу. Поэтому секция `.data` объявляется с `AT (0x00800000)` — это **LMA**, искусственно большой адрес. **VMA** (адрес, по которому ядро будет обращаться) остаётся в `data_mem` с нулевого смещения.

```ld
.data : AT (0x00800000) {
  _gbl_ptr = . + 2048;  ; gp указывает на начало .data + 2K
  *(.data*)
  *(.sdata*)
} > data_mem
```

После компиляции `objcopy -j .data` экспортирует секцию по её **LMA** (`0x00800000`), и я в `init_data.mem` удаляю первую строчку `@xxxx`, чтобы `$readmemh` начал инициализацию с адреса 0 в `data_mem`.

### Стек растёт вниз

```ld
. = LENGTH(data_mem) - _trap_stack_size;
_stack_ptr = ALIGN(16) ...

. = LENGTH(data_mem);
_trap_stack_ptr = ALIGN(16) ...
```

В RISC-V соглашение: **стек растёт от старших адресов к младшим**. То есть `sp` инициализируется максимальным адресом, и каждый `addi sp, sp, -N` уменьшает его. У нас два стека:

- **программный стек** (`_stack_ptr`) — для функций `main`/`int_handler`;
- **стек прерываний** (`_trap_stack_ptr`) — для контекста, сохраняемого при trap.

`_trap_stack_ptr` лежит **выше** в памяти, и они не должны пересечься. В обработчике прерываний делается проверка: если указатель стека прерываний опустился в зону программного стека → `j _endless_loop` (бесконечный цикл для отладки).

### Выравнивание 16

`ALIGN(16)` нужно потому что RISC-V ABI требует, чтобы `sp` всегда был выровнен по 16 байтам. Это позволяет компилятору использовать `addi sp, sp, -16N` и быть уверенным в выравнивании при вызовах `sw`/`lw` с 16-байтными операндами.

## 3. `startup.S` — что и в каком порядке

```assembly
.section .boot
.global _start
_start:
  la    gp, _gbl_ptr      ; 1. инициализация gp (для адресации .data со смещением)
  la    sp, _stack_ptr    ; 2. инициализация sp

  ; 3. зануление .bss секции
  la    t0, _bss_start
  la    t1, _bss_end
_bss_init_loop:
  blt   t1, t0, _irq_config
  sw    zero, 0(t0)
  addi  t0, t0, 4
  j     _bss_init_loop

_irq_config:
  ; 4. настройка вектора прерываний и стека прерываний
  la    t0, _int_handler
  li    t1, -1            ; -1 (все биты единицы) разрешает все источники
  la    t2, _trap_stack_ptr
  csrw  mtvec, t0
  csrw  mscratch, t2
  csrw  mie, t1

  ; 5. вызов main(0, 0)
_main_call:
  li    a0, 0
  li    a1, 0
  call  main

_endless_loop:
  j     _endless_loop
```

### Почему секция `.boot`?

Линкер размещает `.boot` в самом начале `.text`: `_start` оказывается по адресу `0x00000000` — туда указывает `instr_addr_o = 0` при rst.

### Низкоуровневый обработчик прерываний (`_int_handler`)

`mtvec` указывает не на C-функцию `int_handler` напрямую, а на ассемблерный «батут» `_int_handler` в startup.S. Он:

1. Меняет местами `sp ↔ mscratch` (CSR `mscratch` хранит указатель стека прерываний). Теперь sp указывает на стек прерываний.
2. **Сохраняет все caller-saved регистры** (`ra, t0–t6, a0–a7`, кроме `sp`). Caller-saved сохраняем потому, что **высокоуровневая `int_handler` ниже по уровню**, чем main → она «caller» по отношению к функциям, которые сама вызывает, и должна обращаться с caller-saved как со своими.
3. Дополнительно сохраняет `mscratch, mepc, mcause` — на случай вложенного прерывания.
4. `call int_handler` — вызов C-функции.
5. Восстанавливает всё в обратном порядке.
6. `mret` — возврат на сохранённый PC, восстановление `mstatus.MIE`.

**Не сохраняются** callee-saved (`s0–s11`) — это ответственность самой `int_handler`.

## 4. Кросс-компиляция

```bash
riscv32-none-elf-gcc -c -march=rv32i_zicsr -mabi=ilp32 startup.S -o startup.o
riscv32-none-elf-gcc -c -march=rv32i_zicsr -mabi=ilp32 -O2 -ffreestanding -nostdlib main.c -o main.o
riscv32-none-elf-gcc -march=rv32i_zicsr -mabi=ilp32 \
    -Wl,--gc-sections -nostartfiles -T linker_script.ld \
    startup.o main.o -o result.elf
riscv32-none-elf-objcopy -O verilog --verilog-data-width=4 -j .text result.elf init_instr.mem
```

### Ключи

| Ключ | Зачем |
|---|---|
| `-march=rv32i_zicsr` | базовая 32-битная RISC-V + расширение Zicsr (для `csrw`/`csrr`). У нас нет M (умножение), F (float) и т.д. |
| `-mabi=ilp32` | `int`, `long`, указатели = 32 бита, без FP-регистров. |
| `-ffreestanding` | нет стандартной библиотеки C (нет stdio, нет malloc). |
| `-nostdlib` | не линковать с libc. |
| `-Wl,--gc-sections` | выкидывать неиспользуемые функции. |
| `-nostartfiles` | не использовать стандартный crt0 (у нас свой `startup.S`). |
| `-T linker_script.ld` | использовать наш линкер-скрипт. |
| `-O2` | оптимизация. Без неё main и int_handler могут раздуться до десятков инструкций — а у нас память инструкций маленькая. |
| `--verilog-data-width=4` | экспортировать в формате `$readmemh` по 32-битным словам (а не по байтам). |

### Что в `init_instr.mem`

```
@00000000
00001197 ADC18193 76000113 2D000293
...
```

Первая строка `@00000000` — стартовый адрес инициализации памяти (нулевая ячейка `instr_mem`). Каждое последующее слово — 32-битная инструкция в big-endian-нотации hex.

Для `init_data.mem` (если бы он был непустым) я бы **удалил** первую строку `@<address>`, потому что objcopy ставит туда LMA (`0x00800000`), а нам нужно с нуля.

## 5. Доступ к периферии через указатели

В `platform.h`:

```c
typedef volatile struct {
  uint32_t scan_code;            // offset 0x00
  uint32_t scan_code_is_unread;  // offset 0x04
  ...
  uint32_t rst;                  // offset 0x24 (12 слов от 0x00)
} ps2_t;

#define ps2_ptr ((ps2_t *) 0x03000000)
```

### Зачем `volatile`?

Без `volatile` оптимизатор GCC может решить, что `ps2_ptr->scan_code` не меняется между чтениями (он же не знает, что снаружи периферия пишет туда), и **закэшировать значение в регистре**. `volatile` запрещает оптимизатору такие предположения — каждое обращение к полю компилируется в реальный `lw`.

### Как `code = ps2_ptr->scan_code` превращается в `lw`

```c
uint32_t code = ps2_ptr->scan_code;
```

→ компилятор:

```assembly
lui   a4, 0x03000        ; верхние 20 бит адреса 0x03000000
lw    a5, 0(a4)          ; загрузка из памяти по адресу 0x03000000
```

Этот `lw` пойдёт по системной шине → LSU декодирует `addr[31:24] == 0x03` → запрос идёт в `ps2_sb_ctrl` → возвращает scan_code.

## 6. Особенность тестбенча: irq_req пульсом на 1 такт

В моём `lab_14.tb_processor_system.sv`:

```systemverilog
@(posedge clk); irq_req = 1;
@(posedge clk); irq_req = 0;
```

**Почему именно 1 такт?** В `interrupt_controller` (lab-6) сигнал `trap` снимается только когда `irq_pending` залатчился. Но `irq_pending` сбрасывается только при `mret`. То есть пока `irq_req = 1`, как только `mret` отработает, на следующем такте `trap` опять станет 1 — **бесконечный цикл прерываний**.

В реальной системе с PS/2 это не проблема: `ps2_sb_ctrl` сам сбрасывает `interrupt_request_o` после `interrupt_return_i`. Но тестбенч имитирует «голый» источник без сброса, поэтому **сам** даёт пульс ровно 1 такт.

## 7. Что делает программа `ps2_hex` (`main.c`)

```c
void int_handler(void) {
    uint32_t code = ps2_ptr->scan_code;       // 1. читаем scan-код из PS/2
    hex_ptr->hex0 = code & 0xFu;              // 2. младший ниббл → hex0
    hex_ptr->hex1 = (code >> 4) & 0xFu;       // 3. старший ниббл → hex1
    ps2_ptr->rst = 1u;                        // 4. сбрасываем флаг непрочитанного
}

int main(void) {
    while (1) { }                              // ждём прерываний в бесконечном цикле
}
```

Алгоритм:

1. **main** ничего не делает — крутится в `wfi`-эквиваленте (просто `while(1)`).
2. PS/2 контроллер ловит скан-код от клавиатуры → поднимает `interrupt_request_o`.
3. Ядро получает trap → прыгает на `_int_handler` (в startup.S) → тот вызывает C-функцию `int_handler`.
4. `int_handler` читает scan_code, разносит по `hex0`/`hex1`, сбрасывает PS/2.
5. `mret` → ядро возвращается в `main`.
6. На семисегментниках видим младший и старший ниблы скан-кода.

## 8. Типичные вопросы преподавателя

**Q: Почему в `main` нельзя использовать `printf`?**
A: `printf` — функция стандартной libc, которой у нас нет (`-nostdlib`). Она тащит за собой forking, buffered I/O, va_args, форматирование... — десятки KB кода, что не влезет в нашу 1KB память инструкций. Альтернатива — лёгкий `printf` (https://github.com/mpaland/printf) с одной функцией `_putchar` для UART/VGA.

**Q: Почему нужно `extern "C"` в C++?**
A: В C++ имена функций **манглируются** (mangling) — добавляются префиксы типов. `void int_handler()` в C++ становится `_Z11int_handlerv`. Линкер не найдёт `int_handler`, который зовёт `call int_handler` из `startup.S`. `extern "C"` отключает mangling для этой функции.

**Q: Зачем `int main(int argc, char** argv)`, если в startup.S мы передаём `a0=0, a1=0`?**
A: Это **формальный** прототип `main`, унаследованный от C-стандарта. У нас нет ОС, нет argv. Я в своей программе использую `int main(void)` — компилятор согласен на оба варианта.

**Q: Что если в `int_handler` я вызову другую функцию?**
A: GCC сгенерирует `call` инструкцию. Внутри другой функции `ra` сохранится правильно, потому что мы пришли через `_int_handler` (батут), а тот сохраняет `ra` ДО `call int_handler`. То есть **вложенные вызовы из обработчика работают**.

**Q: А если внутри `int_handler` опять придёт прерывание?**
A: Не придёт. CSR-контроллер при trap делает `mstatus.MIE = 0` — глобально запрещает прерывания. До `mret` ядро прерывания не принимает. Это защита от reentrant trap.

**Q: Почему вы не пишете `csr_w mie, 0x100` (бит 8 = MEIE), а пишете `csrw mie, -1`?**
A: Потому что в нашем упрощённом `interrupt_controller` (lab-6) проверяется `|mie_reg` — любой ненулевой `mie` разрешает прерывания. Мы не различаем типы (machine timer / external / software). Поэтому `-1` (все биты единицы) — это «разрешить все типы», и оно работает.

**Q: Что такое `gp` и зачем он?**
A: `gp` (global pointer) указывает на середину секции `.data`. Компилятор использует **смещённую адресацию относительно gp** для глобальных переменных в пределах ±2 КБ. Это сокращает число инструкций: вместо `lui+addi+lw` (3 инструкции) получается просто `lw rd, off(gp)` (1 инструкция).

**Q: Что делает `_endless_loop` в конце startup.S?**
A: Защита от того, что `main` вернулась. Если бы мы не зациклили процессор, он начал бы выполнять то, что после `main` (мусор или undefined). Зацикливание — это «программный wfi».
