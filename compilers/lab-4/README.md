### Грамматика C-light (из методички)

```
<program>: <type>   'main'   '('   ')'   '{'   <statement>   '}'
<type>: 'int' | 'bool' | 'void'
<statement>:
  | <declaration> ';'
  | '{' <statement> '}'
  | <for>   <statement>
  | <if>      <statement>
  | <return>
<declaration>: <type>   <identifier>   <assign>
<identifier>: <character><id_end>
<character>: 'a' | ... | 'z' | 'A' | ... | 'Z' | '_'
<id_end>: | <character><id_end>
<assign>: | '=' <assign_end>
<assign_end>: <identifier> | <number>
<number>: <digit><number_end>
<digit>: '0' | ... | '9'
<number_end>: | <digit><number_end>
<for>: 'for' '(' <declaration> ';' <bool_expression> ';' ')'
<bool_expression>: <identifier>   <relop>    <identifier>
  | <number>      <relop>    <identifier>
<relop>: '<' | '>' | '==' | '!='
<if>: 'if' '(' <bool_expression> ')'
<return>: 'return' <number> ';'
```

`<N1><N2>` — конкатенация без пробелов, `<N1>   <N2>` — через пробельные символы (как в C). Стартовый символ — `<program>`.

### Особенности грамматики, которые пришлось учесть

1. **`<statement>` — это один оператор, а не список.** В блоке `{ }` ровно один оператор, тело `main` тоже.
   Несколько операторов подряд пишутся только через вложенность: `for (...) if (...) { return 0; }`.
   Программа `{ int a = 1; int b = 2; }` по этой грамматике ошибочна (пример `err_block.cl`).
2. **`<statement>` может быть пустым.** Поэтому `int main() { }` и `if (a < b) }` — правильные конструкции.
   Пустой оператор допустим только перед `}`: FOLLOW(`<statement>`) = { `}` }.
3. **`<for>` заканчивается на `; )`:** `for (int i = 0; i < n;)` — третьей части заголовка нет, а после `)`
   идёт оператор-тело. В `<for>` первая часть — обязательно объявление с типом.
4. **Справа от операции сравнения — только идентификатор.** `i < 10` — ошибка, `10 > i` — правильно.
5. **`<return>` сам содержит `;`** и допускает только число: `return 0;` верно, `return x;` — ошибка.
6. **В идентификаторе нет цифр:** `<character>` — только буквы и `_`, поэтому `x1` — лексическая ошибка.
7. Ключевые слова (`int bool void main for if return`) зарезервированы, как в C. Иначе `int int = 5;`
   было бы неоднозначно: по символьной грамматике `int` подходит и под `<identifier>`.

## Преобразования грамматики

**1. Разделение на лексический и синтаксический уровни.** Правила для `<identifier>`, `<number>`, `<character>`,
`<digit>`, `<id_end>`, `<number_end>` записаны через конкатенацию без пробелов и праволинейны
(`<id_end>: ε | <character><id_end>`), то есть задают регулярные языки. Их распознаёт лексер (конечный автомат),
а для LL(1)-анализатора `<identifier>` и `<number>` становятся терминалами `id` и `num`. Пробельные символы между
токенами тоже съедает лексер. Так делают все компиляторы, и только так таблица разбора получается разумного
размера: на уровне символов в ней было бы 60+ столбцов (`a`…`z`, `A`…`Z`, `0`…`9`).

**2. Проверка на LL(1).** Грамматика годится для предиктивного разбора, если для каждой пары альтернатив
A → α | β: FIRST(α) ∩ FIRST(β) = ∅, а если одна из них порождает ε, то FIRST другой не пересекается с FOLLOW(A).

- **Левой рекурсии нет:** ни одна продукция не начинается со своего же нетерминала.
- **Левая факторизация не нужна.** Единственное место, где она приходит в голову, — `<bool_expression>`: у двух
  альтернатив общий хвост `<relop> <identifier>`. Но факторизация выносит общий *префикс*, а префиксы здесь
  разные — `id` и `num`, FIRST не пересекаются, выбор делается по первому токену. Можно переписать
  `<bool_expression> → <operand> <relop> id`, `<operand> → id | num`, но на LL(1)-свойство это не влияет,
  поэтому оставлена запись из методички.
- **ε-альтернативы:** `<statement>` (FIRST остальных = { int bool void { for if return }, FOLLOW = { } }),
  `<assign>` (FIRST(`= …`) = { = }, FOLLOW = { ; }). Пересечений нет.
- Остальные нетерминалы выбирают альтернативу по разным ключевым словам или знакам.

Программа строит таблицу автоматически и проверяет, нет ли ячеек с двумя продукциями. Конфликтов нет —
**грамматика LL(1) без изменений**, методичка не ошиблась. Получилась такая грамматика над токенами (24 продукции):

```
 1. <program> → <type> main ( ) { <statement> }
 2. <type> → int
 3. <type> → bool
 4. <type> → void
 5. <statement> → ε
 6. <statement> → <declaration> ;
 7. <statement> → { <statement> }
 8. <statement> → <for> <statement>
 9. <statement> → <if> <statement>
10. <statement> → <return>
11. <declaration> → <type> id <assign>
12. <assign> → ε
13. <assign> → = <assign_end>
14. <assign_end> → id
15. <assign_end> → num
16. <for> → for ( <declaration> ; <bool_expression> ; )
17. <bool_expression> → id <relop> id
18. <bool_expression> → num <relop> id
19. <relop> → <
20. <relop> → >
21. <relop> → ==
22. <relop> → !=
23. <if> → if ( <bool_expression> )
24. <return> → return num ;
```

### Расширение языка (флаг `--ext`)

Преподаватель разрешил расширять язык. Без расширения на C-light нельзя написать даже два объявления подряд,
поэтому с флагом `--ext` в блоке разрешена последовательность операторов, а пустой оператор пишется как `;`:

```
<program> → <type> main ( ) { <stmts> }
<stmts>   → <statement> <stmts> | ε
<statement> → <declaration> ; | { <stmts> } | <for> <statement> | <if> <statement> | <return> | ;
```

Пустая альтернатива перенесена из `<statement>` в `<stmts>`: если оставить её в `<statement>`, то
`<stmts> → <statement> <stmts>` даст конфликт на `}`. Эта грамматика тоже LL(1) (проверяется тем же кодом),
таблица — [`results/parse_table_ext.md`](results/parse_table_ext.md). По умолчанию анализатор работает строго
по грамматике из методички.

Считаются по правилам из методички итерациями до неподвижной точки (`grammar.hpp`, `buildTables`).

## Анализатор

Нерекурсивный предиктивный анализатор ровно по рис. 1 и алгоритму из методички: стек (изначально `$ <program>`),
входной буфер токенов с `$` на конце и таблица M. На каждом шаге смотрим на вершину стека X и текущий токен a:

- X = a = `$` — разбор окончен;
- X — терминал и X = a — снимаем X, сдвигаем вход;
- X — нетерминал и M[X, a] = X → Y1…Yk — заменяем X на Yk…Y1 (Y1 на вершине), выводим продукцию;
- иначе — ошибка, вызывается процедура восстановления.

Каждый шаг записывается строкой таблицы «Стек / Вход / Примечание».

## Восстановление после ошибок

### Режим паники (обязательный, по умолчанию)

Правила из примера 3 методички:

| Ситуация | Действие |
| --- | --- |
| нетерминал A, M[A, a] = `synch` | A снимается со стека («неполная конструкция») |
| нетерминал A, M[A, a] пусто | токен a пропускается («неожиданный символ») |
| терминал t на вершине ≠ a | t снимается со стека («пропущен символ») или пропускается a — см. ниже |
| вход кончился (`$`), а стек нет | символы снимаются со стека («неожиданный конец файла») |
| стек кончился (`$`), а вход нет | токены пропускаются («текст после конца программы») |

**Синхронизирующие множества** выбраны по эвристикам из методички:

1. synch(A) = FOLLOW(A) — после A обычно идёт что-то из FOLLOW(A);
2. для нетерминалов ниже уровня оператора (`<declaration>`, `<assign>`, `<bool_expression>`, `<relop>`, …)
   добавлены символы, с которых начинается оператор (`int bool void for if return {`), и `}`. Иначе забытая
   `;` перед `if` заставила бы выбросить весь следующий оператор;
3. FIRST(A) добавлять не нужно: на этих символах в M[A, a] уже стоит продукция;
4. `$` есть в каждом synch — дальше конца файла пропускать нечего.

**Несовпадение терминала.** Методичка предлагает просто снимать терминал со стека (считать его пропущенным).
Это плохо работает, когда на его месте стоит лишний токен: при `return x;` анализатор снял бы `num`, потом `;`,
потом `}`… Поэтому синхронизирующее множество терминала t — это {t} ∪ FIRST(того, что лежит в стеке под t):

- если a может идти сразу после t — значит, t пропущен: снимаем t (`for (int i = 0 i < n;)` — пропущена `;`);
- если a — «сильный» разделитель (`; } ) { for if return int bool void`) и его ждёт кто-то глубже в стеке —
  тоже снимаем t;
- иначе a — мусор: пропускаем его (`return x;` — пропускаем `x`, потом `;` встаёт на место).

**Продукция по умолчанию.** У `<program>` и `<declaration>` всего одна продукция, и она начинается с `<type>`.
Если ячейка пуста (например, программа начинается с `main` без типа), продукция всё равно раскрывается, и ошибку
сообщает `<type>`: «перед 'main' ожидалось: тип». Иначе пришлось бы выбросить всю программу. Это аналог
совета методички использовать ε-продукцию по умолчанию. В таблице такие ячейки помечены `(k)`.

**Подавление лавины ошибок.** Как советует методичка, после обнаружения ошибки новые сообщения не выдаются, пока
анализатор не примет хотя бы один токен. Все действия при восстановлении пишутся в таблицу хода разбора с пометкой
«восстановление», а пропущенные токены выводятся под сообщением об ошибке.

**Почему не зацикливается.** Каждое действие при ошибке либо снимает символ со стека, либо съедает токен,
а между ошибками работает обычный LL(1)-разбор (грамматика без левой рекурсии). На всякий случай в цикле есть
предохранитель по числу шагов; на примерах и на 1500 случайных программах (×4 режима) под AddressSanitizer
и UBSan он ни разу не сработал.

### Режим фразы (дополнение, флаг `--phrase`)

Ошибочные ячейки таблицы (пустые и synch) заполняются «указателями на процедуры», которые правят один токен
(вставка, удаление, замена). Например, M[`<type>`, id] = synch, но если за id идёт ещё один id, это не
пропущенный тип, а неизвестный. Если ни одна процедура не подходит, работает режим паники.

| Где | Условие | Правка, тип ошибки |
| --- | --- | --- |
| M[`<relop>`, `=`] | — | `=` заменяется на `==` («замена символа») |
| M[`<type>`, id] | дальше снова id (`x i = 0`) | `x` считается типом («неизвестный тип») |
| M[`<statement>`, id] | дальше `=` или `;` (`x = 3;`) | вставляется тип («объявление без типа») |
| M[`<statement>`, id] | дальше id (`float f = 2;`) | `float` считается типом («неизвестный тип») |
| M[A, a], любая | M[A, b] не пуст для следующего токена b | a удаляется («лишний символ») |
| терминал t ≠ a | следующий токен = t | a удаляется («лишний символ») |
| терминал t ≠ a | a может идти после t | t вставляется («пропущен символ») |
| терминал t ≠ a | следующий токен может идти после t | a заменяется на t («замена символа»), `return x;` |

Защита от зацикливания та же: каждая правка съедает токен или снимает символ со стека. Единственная правка,
которая кладёт символы в стек (объявление без типа: `id <assign> ;`), кладёт сверху `id`, и следующим же шагом
он совпадает с текущим токеном.

## Типы ошибок

| Категория | Тип | Пример |
| --- | --- | --- |
| лексическая | недопустимый символ | `@`, `,`, `+`, кириллица |
| лексическая | неверный идентификатор | `x1` (цифры в идентификаторе запрещены) |
| лексическая | неверное число | `12ab` |
| лексическая | неподдерживаемая операция | `<=`, `>=`, одиночный `!` |
| лексическая | незакрытый комментарий | `/*` без `*/` |
| синтаксическая | пропущен символ | `int a = 1` без `;` |
| синтаксическая | неожиданный символ | `return x;` (паника) |
| синтаксическая | неполная конструкция | `if (a b)` — нет операции сравнения |
| синтаксическая | неожиданный конец файла | файл оборвался внутри `main` |
| синтаксическая | текст после конца программы | лишняя `}` в конце |
| синтаксическая (фраза) | лишний символ, замена символа, объявление без типа, неизвестный тип | см. таблицу выше |

Лексер после ошибки не останавливается: чужой символ выбрасывается, а `x1` и `12ab` всё равно выдаются как `id`
и `num`, `<=` — как `<`, одиночный `!` — как `!=`. Так одна опечатка даёт одну ошибку, а не лексическую плюс
синтаксическую. Комментарии `//` и `/* */` разрешены: в C они считаются пробельными символами, а методичка
говорит, что пробельные символы в C-light такие же, как в C.

## Как запустить

Один раз в корне репозитория (там `.envrc` с `use flake`, g++ и make берутся из `flake.nix`):

```bash
cd ~/repos/uni
direnv allow
```

Дальше:

```bash
cd compilers/lab-4
make                                # собрать ./lab4
./lab4 examples/ok.cl               # режим паники, грамматика из методички
./lab4 --phrase examples/err_multi.cl       # режим фразы
./lab4 --ext examples/ext_errors.cl         # расширенная грамматика
./lab4 --table                      # только таблица M → results/parse_table.md
make test                           # все примеры в обоих режимах
```

Без direnv: `nix develop -c make` и `nix develop -c make test`.

Ключи: `--phrase` — режим фразы, `--ext` — расширенная грамматика, `--out DIR` — куда писать файлы
(по умолчанию `results/`), `--table` — только построить таблицу. Код возврата 0 — ошибок нет, 1 — есть ошибки.

**Выходные файлы:**

- `results/<имя>.trace.md` — таблица хода разбора (как в примере 4) в режиме паники, `results/<имя>.phrase.trace.md` —
  в режиме фразы. В начале файла — исходный текст и список ошибок, дальше таблица «№ / Стек / Вход / Примечание».
  Стек записан как в методичке: дно `$` слева, вершина справа. Вход показан лексемами, длинный хвост сокращён до 10 токенов;
- `results/parse_table.md` (`parse_table_ext.md` для `--ext`) — продукции, FIRST, FOLLOW, synch, таблица M,
  результат проверки LL(1), описание процедур режима фразы.

### Таблица хода разбора (`results/err_header.trace.md`)

Программа `main( { return 0; }` — нет типа и нет `)`. Таблица в формате примера 4 методички:

| №   | Стек                                | Вход                      | Примечание                                                                                                                                    |
|-----|-------------------------------------|---------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------|
| 1   | `$ <program>`                       | `main ( { return 0 ; } $` | `M[<program>, main]` пусто, у `<program>` одна продукция — раскрываем её по умолчанию: `<program> → <type> main ( ) { <statement> }`          |
| 2   | `$ } <statement> { ) ( main <type>` | `main ( { return 0 ; } $` | Ошибка 1 (неполная конструкция: перед 'main' ожидалось: тип ('int', 'bool', 'void')), `M[<type>, main]` = synch → `<type>` снимается со стека |
| 3   | `$ } <statement> { ) ( main`        | `main ( { return 0 ; } $` | совпадение 'main'                                                                                                                             |
| 4   | `$ } <statement> { ) (`             | `( { return 0 ; } $`      | совпадение '('                                                                                                                                |
| 5   | `$ } <statement> { )`               | `{ return 0 ; } $`        | Ошибка 2 (пропущен символ: ожидалось: ')' перед '{') → снимаем ')' со стека                                                                   |
| 6   | `$ } <statement> {`                 | `{ return 0 ; } $`        | совпадение '{'                                                                                                                                |
| 7   | `$ } <statement>`                   | `return 0 ; } $`          | `<statement> → <return>`                                                                                                                      |
| 8   | `$ } <return>`                      | `return 0 ; } $`          | `<return> → return num ;`                                                                                                                     |
| 9   | `$ } ; num return`                  | `return 0 ; } $`          | совпадение 'return'                                                                                                                           |
| 10  | `$ } ; num`                         | `0 ; } $`                 | совпадение '0'                                                                                                                                |
| 11  | `$ } ;`                             | `; } $`                   | совпадение ';'                                                                                                                                |
| 12  | `$ }`                               | `} $`                     | совпадение '}'                                                                                                                                |
| 13  | `$`                                 | `$`                       | Разбор завершён, синтаксических ошибок: 2                                                                                                     |

Шаг 1 — продукция по умолчанию, шаг 2 — `M[<type>, main] = synch`, `<type>` снимается со стека (как `M[F, +] = synch`
в примере 4), шаг 5 — пропущенный терминал `)` снимается со стека. Остальные таблицы — в [`results/`](results).

## Выводы

Грамматика C-light из методички оказалась LL(1) без преобразований (после выноса идентификаторов и чисел в лексер),
поэтому анализатор полностью табличный: таблица M строится программой по FIRST и FOLLOW, а не пишется руками.
Режим паники с synch-множествами на основе FOLLOW плюс начала операторов позволяет пройти программу до конца и
найти все ошибки в примерах; подавление сообщений до первого принятого токена убирает лавину ложных ошибок.
Режим фразы даёт более точные сообщения («`=` вместо `==`», «неизвестный тип») и в одном случае из примеров
не насчитывает лишнюю ошибку.
