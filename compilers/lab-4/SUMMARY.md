# ЛР4. Анализатор C-light с восстановлением после ошибок — коротко

Шпаргалка «на пальцах». Полный отчёт — [README.md](README.md), теория — [THEORY.md](THEORY.md).

## Суть

Нужно проверить программу на C-light и найти **все** ошибки, а не только первую. Анализатор табличный
(LL(1)): у него есть стек и таблица M[A, a] — «если на вершине стека нетерминал A, а на входе токен a,
то раскрой A по такой-то продукции». Таблицу программа строит сама по множествам FIRST и FOLLOW.
Если в ячейке пусто — ошибка. Дальше включается **режим паники**: выбрасываем токены со входа или
символы со стека, пока не дойдём до «синхронизирующего» токена (`;`, `}`, начало оператора) и разбор
снова не пойдёт. Программа написана дважды — на C++ (`cpp/`) и на Python (`python/`), вывод у них одинаковый.

## Что делает программа

| Этап | C++ / Python | Что получается |
| --- | --- | --- |
| Лексер | `lexer.hpp` / `lexer.py` | токены `int`, `id`, `num`, `(`, `==`… со строкой и столбцом; лексические ошибки (`x1`, `12ab`, `@`, `<=`) |
| FIRST, FOLLOW | `grammar.hpp` / `grammar.py` | считаются итерациями по 24 продукциям, пока множества растут |
| Таблица M | `grammar.hpp` / `grammar.py` | 11 нетерминалов × 20 терминалов, конфликтов нет → грамматика LL(1) |
| Разбор | `parser.hpp` / `parser.py` | цикл по рис. 1 методички + восстановление (паника или фраза) |
| Вывод | `main.cpp` / `main.py` | ошибки с местом и типом, `results/*.trace.md` (как пример 4), `results/parse_table.md` |

## Вывод и откуда он

- **Грамматика LL(1) без преобразований.** `<identifier>` и `<number>` записаны без пробелов, то есть это
  лексика: их забирает лексер, парсеру остаются токены `id` и `num`. У `<bool_expression>` альтернативы
  начинаются с разных токенов (`id` и `num`), поэтому факторизация не нужна. ε есть у `<statement>` и
  `<assign>`, но их FOLLOW (`}` и `;`) не пересекается с FIRST других альтернатив.
- **Все ошибки находятся.** `make test`: 13 примеров × 2 режима + проверка LL(1) двух грамматик = 28 из 28,
  у обеих версий. В `err_multi.cl` 7 ошибок: паника находит 8 (одну считает дважды), режим фразы — ровно 7.
- **Лавины ложных ошибок нет:** после ошибки новые сообщения молчат, пока не будет принят хоть один токен.
- **Версии совпадают байт в байт:** на примерах и на 1100 случайных испорченных программах во всех 4 режимах.

## Как рассказывать

> «Я разделил грамматику на два уровня: идентификаторы и числа распознаёт лексер, остальное — LL(1)-анализатор
> со стеком, как на рис. 1. FIRST, FOLLOW и таблица M строятся программой, конфликтов нет, значит, грамматика
> LL(1). При ошибке работает режим паники: если в ячейке synch — снимаю нетерминал со стека, если пусто —
> пропускаю токен, если терминал не совпал — либо считаю его пропущенным, либо выбрасываю мусорный токен.
> Synch-множества — это FOLLOW плюс начала операторов и `}`. Ход разбора пишется в таблицу как в примере 4.
> Дополнительно сделал режим фразы: он чинит один токен — `=` на `==`, вставляет `;`, заменяет неизвестный тип».

## Возможные вопросы

- **Почему грамматика LL(1)?** Ни в одной ячейке M нет двух продукций — программа это проверяет
  (`conflicts` пуст). Левой рекурсии нет, альтернативы различаются по первому токену.
- **Что такое synch и откуда он?** Токены, на которых нетерминал можно бросить и продолжить: FOLLOW(A), плюс
  для «мелких» нетерминалов — `int bool void for if return { }`, иначе забытая `;` съест следующий оператор.
- **Что делаешь, если терминал на вершине не совпал?** Если токен может идти сразу после терминала — терминал
  пропущен, снимаю его. Иначе токен — мусор, пропускаю его (`return x;` → выбросить `x`).
- **Почему не зациклится?** Каждое действие при ошибке либо снимает символ со стека, либо съедает токен.
- **Зачем «продукция по умолчанию»?** `main() {...}` без типа: ячейка M[`<program>`, main] пустая, по правилам
  паники выбросили бы всю программу. А так раскрываем единственную продукцию, и `<type>` говорит «нет типа».
- **Чем фраза лучше паники?** Правит один токен и даёт точное сообщение («`=` вместо `==`»), а не выбрасывает
  куски. Минус — может угадать не то, поэтому каждая правка проверяется по следующему токену.
- **Почему `{ int a; int b; }` — ошибка?** В методичке `'{' <statement> '}'` — ровно один оператор.
  Последовательности я добавил расширением `--ext`.
- **Чем отличаются версии?** Алгоритм один; Python запускается без сборки. Отличия технические: `std::set`
  против `set` + `sorted`, а байты исходника Python переводит в `str` через `surrogateescape`, чтобы столбцы
  и вывод совпали с C++ до байта.

**Цикл разбора (`python/parser.py`, 97–140):**

```python
97   while True:                               # ЦИКЛ repeat ... until X = $
103      X = stack[-1]                         # вершина стека
106      if X == "$":                          # РАЗВИЛКА: стек пуст
107          if a.kind == "$": ... break       #   и вход пуст — конец разбора
117      elif not g.is_nonterminal(X):         # РАЗВИЛКА: терминал
118          if X == a.kind: pop; ip += 1; recovering = False   # совпал — сдвиг
124          else: ... panic_terminal(X, a)    #   не совпал — восстановление
126      k = g.cell(X, a.kind)                 # нетерминал: смотрим M[X, a]
127      if k >= 0: pop; stack.extend(reversed(rhs))           # раскрываем
140      else: ... panic_nonterminal(X, a)     # пусто или synch
```

**Режим паники (`python/parser.py`, 151–171):**

```python
151 if self.insertable(a.kind): report_missing; stack.pop()   # РАЗВИЛКА: t пропущен
155 report("неожиданный символ"); self.skip()                 # иначе выбросить a
162 if a.kind == "$" or a.kind in g.synch[A]:                 # РАЗВИЛКА: synch
167     self.stack.pop()                                      #   снять A
170 report("неожиданный символ"); self.skip()                 # пусто — пропустить a
```

Флаг `recovering` сбрасывается при совпадении токена (C++ — строка 69, Python — 122).
