## Задание

Написать программу, реализующую работу недетерминированного магазинного автомата.

Входные данные:

1. Текстовый файл с грамматикой. В строке может быть несколько правил с одной левой частью,
   они разделяются `|`. Левая часть отделяется от правой символом `>`; если `>` в строке несколько,
   первый — разделитель, остальные — терминалы. Нетерминалы — заглавные латинские буквы, все
   остальные символы — терминалы. Правил сколько угодно. Пробелы рекомендуется считать незначащими,
   а терминал «пробел» обозначать другим символом (например, `~`).
2. Строка, которую нужно проанализировать построенным автоматом.

Выходные данные на «отлично»: значения множеств P, Z и т.д.; список команд (1)–(4) из раздела
«Построение магазинного автомата»; цепочка конфигураций автомата, полученная при его работе;
заключение о допустимости (или недопустимости) цепочки.

## Как запустить

Тулчейн (g++, make) берётся из `flake.nix` в корне репозитория:

```bash
cd ~/repos/uni
direnv allow                      # один раз: .envrc содержит `use flake`
cd compilers/lab-3
make                              # собирает ./lab3 (g++ -std=c++20 -Wall -Wextra -O2)
./lab3 examples/test2.txt         # дальше вводить цепочки по одной, пустая строка — выход
make test                         # 100 проверок, см. раздел «Тесты»
make clean
```

Без direnv: `nix develop -c make` и `nix develop -c ./lab3 examples/test2.txt`.

Цепочки можно подать и не интерактивно: `printf 'a+a*a\na+\n' | ./lab3 tests/expr.txt`.
Пустую цепочку вводим как `ε` (пустая строка означает конец ввода). Если во входной цепочке есть
символ вне печатного ASCII (кириллица, `€`), он заведомо не входит в P, и программа сразу пишет, что
цепочка не допускается.

В `Makefile` компилятор задан жёстко (`CXX = g++`, а не `?=`): во flake переменная окружения `CXX`
указывает на кросс-компилятор `riscv32-none-elf-g++` для микропроцессорных лаб, и с `?=` получался
бинарь под RISC-V, который здесь не запускается.

## Формат грамматики и принятые решения

| Вопрос | Решение |
| --- | --- |
| Разделитель частей правила | первый `>` в строке; остальные `>` — терминалы (`C>a\|b\|c\|0\|>` из `test1.txt`) |
| Альтернативы | через `\|`; несколько строк с одной левой частью объединяются; повторная альтернатива отбрасывается |
| Начальный символ I | левая часть **первого** правила файла (в методичке так и есть: E в примере с E, T, F) |
| Нетерминалы | заглавные латинские `A`–`Z`; левая часть — ровно одна такая буква |
| Терминалы | все остальные печатные ASCII-символы, кроме `\|` и `~` |
| Пробелы, табуляции, `\r` | незначащие и выбрасываются (файлы преподавателя сохранены с CRLF) |
| Терминал «пробел» | `~` в файле; в выводе тоже показывается как `~`. Апострофы не поддерживаются: один способ проще объяснить и проверить |
| ε-правило | пустая альтернатива: `S > aSbS \|` означает S → aSbS \| ε |
| Пустые строки файла | пропускаются |

Пробелы во **входной цепочке**: если в грамматике есть терминал-пробел, то `~` во вводе означает
пробел, а настоящие пробелы сохраняются. Если такого терминала нет, пробелы во вводе отбрасываются —
как в методичке, где цепочка записана «a + a*a», а в конфигурациях стоит `a+a*a`.

Ошибки в файле грамматики выводятся с номером строки, программа завершается с кодом 1:

| Ошибка | Сообщение |
| --- | --- |
| нет `>` | `строка 2: нет символа '>', отделяющего левую часть правила от правой` |
| левая часть не одна заглавная буква (`ab>c`, `e>a`, `>a`) | `строка 2: левая часть «ab» должна быть одной заглавной латинской буквой` |
| нетерминал справа без правил | `строка 1: нетерминал T встречается в правой части, но правил для него нет` |
| кириллица, управляющие символы | `строка 1: допустимы только печатные ASCII-символы (пробел-терминал записывается как ~)` |
| в файле нет правил | `в файле нет ни одного правила` |
| файл не открывается | `не удалось открыть файл «…»` |

Если из какого-то нетерминала не выводится ни одной терминальной цепочки (`B > bB`), это не ошибка,
а предупреждение: грамматика допустима, просто ветви с B всегда тупиковые.

## Построение автомата

Строго по разделу «Построение магазинного автомата» методички. Для грамматики G = {VN, VT, I, P}:

- S = {s0}, P = VT, Z = VN ∪ VT ∪ {h0}, F = {s0}, начальное состояние s0, маркер дна h0;
- команды типа (1): для каждого нетерминала A с правилами A → α₁ | … | αₖ —
  δ0(s0, ε, A) = {(s0, α₁ᴿ); …; (s0, αₖᴿ)}, где αᴿ — реверс (вершина магазина справа, поэтому
  правую часть кладём задом наперёд, и первым наверху оказывается её первый символ);
- команды типа (2): для каждого терминала a — δ(s0, a, a) = (s0, ε);
- команда типа (3): δ(s0, ε, h0) = (s0, ε);
- тип (4) — начальная конфигурация (s0, α, h0I).

Нумерация как в примере методички: сначала по одной команде (1) на нетерминал в порядке появления
в файле, потом команды (2) для терминалов, последней — команда (3). Если у нетерминала несколько
альтернатив, в цепочке конфигураций пишется номер подпункта: `(1.2)` — вторая альтернатива команды (1),
так же записано `(6.2)` в примере с автоматом M2.

Заключительная конфигурация — (s0, ε, ε): вход прочитан, магазин пуст, s0 ∈ F.

Одно расхождение с текстом методички: там команда для F записана как `(s0, (E))`, без реверса. Это
опечатка — по правилу (1) должен быть реверс `)E(`, иначе первой в вершине окажется `)`. Программа
печатает `)E(`, а цепочка конфигураций для `a+a*a` совпадает с методичкой такт в такт.

Номера команд типа (2) отличаются от примера: в методичке терминалы перечислены в порядке
a, +, *, (, ), и команда для `a` получила номер (4); программа нумерует терминалы в порядке первого
появления в файле (+, *, (, ), a), поэтому у неё `a` — это (8). Сами команды те же, правила выбора
порядка в методичке нет.

Обозначения S, P, F у автомата совпадают с буквами, которые могут быть нетерминалами грамматики
(например, P и S в `test1.txt`). Это обозначения методички, и я их не менял: в выводе множества
автомата всегда идут в блоке «Магазинный автомат M», нетерминалы — в блоке «Грамматика».

## Как ищется цепочка конфигураций

Автомат недетерминированный: когда в вершине нетерминал, применимы сразу все его альтернативы.
Цепочка допустима, если **хоть одна** последовательность тактов приводит в (s0, ε, ε). Программа
ищет её перебором в глубину с возвратом (функция `search`, проверки шага — в `enter`):

1. в вершине h0 — применяем команду (3);
2. в вершине терминал — если он совпадает с текущим символом входа, команда (2), иначе тупик;
3. в вершине нетерминал — пробуем альтернативы по порядку, как они записаны в файле; если ветка не
   дошла до конца, снимаем её конфигурации с пути и пробуем следующую.

Как только найдена заключительная конфигурация, путь от начальной до неё и есть ответ.

Перебор написан без рекурсии: текущая ветвь лежит в векторе `path_`, и у каждой конфигурации на ней
записано, сколько переходов из неё уже испробовано. У рекурсивного перебора глубина рекурсии равна
длине ветви (а она больше длины входа), и на цепочке из нескольких тысяч символов переполняется стек
вызовов.

### Защита от зацикливания

Простой перебор на левой рекурсии не останавливается: при E → E+T автомат заменяет E на T+E, в
вершине снова E, и так до бесконечности. Поэтому перед тем как идти дальше из конфигурации, она
проверяется пятью отсечениями. Все они только выбрасывают ветви, которые **заведомо** не могут
закончиться успехом, поэтому ответ «допускается / не допускается» от них не меняется.

| № | Отсечение | Почему оно корректно | От чего спасает |
| --- | --- | --- | --- |
| 1 | конфигурация уже встречалась (множество `visited_`) | автомат с одним состоянием дальше ведёт себя одинаково из одинаковых конфигураций; если она уже проверена — повтор ничего не даст, если проверяется выше по ветви — это цикл | цепные циклы A → B, B → A |
| 2 | **по длине**: сумма minLen символов магазина больше остатка входа | каждый символ магазина когда-нибудь превратится в терминальную цепочку длиной не меньше minLen (у терминала — 1) | левая рекурсия E → E+T: каждый виток добавляет +T, т.е. ещё 2 символа |
| 3 | **по составу**: какого-то терминала в магазине больше, чем его осталось во входе | каждый терминал в магазине будет прочитан командой (2) | та же рекурсия: плюсов в магазине не может быть больше, чем во входе |
| 4 | **по хвосту**: терминалы, лежащие подряд у самого дна, не совпадают с концом входа | они будут прочитаны последними и именно в таком порядке | рекурсия S → Sa \| Sb (test3): без этого перебирается 2ⁿ вариантов «хвоста» |
| 5 | **по высоте магазина**: в магазине больше 2 + (n+1)·\|VN\|·(maxRhs−1) символов | см. ниже | левая рекурсия через обнуляемый символ: S → SA, A → ε |

minLen(A) — длина самой короткой терминальной цепочки, выводимой из A. Считается заранее
итерациями до неподвижной точки: minLen(A) = min по правилам A → X₁…Xₖ суммы minLen(Xᵢ). Для
грамматики из методички minLen(E) = minLen(T) = minLen(F) = 1, для `test1.txt` minLen(E) = 3.

Откуда граница в отсечении 5. Если цепочка выводима, у неё есть дерево вывода с минимальным числом
узлов. В нём на пути от корня к листу не бывает двух узлов с одним и тем же нетерминалом и одной и той
же кроной (иначе верхнее поддерево можно заменить нижним и дерево станет меньше). Кроны узлов на пути
вложены друг в друга, поэтому одинаковой длины они только если совпадают; длин всего n+1 (от 0 до n),
так что внутренних узлов на пути не больше (n+1)·|VN|. Автомат, моделирующий левый вывод по этому
дереву, держит в магазине только «правых братьев» узлов текущего пути — не больше maxRhs−1 на узел, —
плюс h0 и вершину. Значит, в высоту отсечения 5 укладывается хотя бы один успешный путь. Без ε-правил
отсечение 2 строже (все символы магазина дают ≥ 1 символ входа), и отсечение 5 не срабатывает ни разу.

С отсечениями 2 и 5 число возможных конфигураций конечно (позиция ≤ n, магазин ограничен), а
отсечение 1 не даёт зайти ни в одну дважды, поэтому перебор всегда заканчивается. Как
предохранитель от очень длинных строк стоит ещё лимит 2 000 000 конфигураций: если он исчерпан,
программа честно пишет «допустимость не установлена». В тестах лимит не достигается: самая тяжёлая
цепочка `(((a+a)*(a+a))*((a+a)*(a+a)))+a*(a+a*(a+a))` (43 символа) укладывается в 388 тыс.
конфигураций и полсекунды. Достигается он на длинных цепочках с левой рекурсией: на отвергаемой
`a+a+…+a+` из 4000 символов в грамматике методички или на допустимой `bbb…ba` из 3000 символов в
`test3.txt` (там число конфигураций растёт как n²/2: 1000 символов — 505 тыс.). Перебор с
возвратом в худшем случае экспоненциален, это свойство метода, а не ошибка. Хуже всего грамматики,
где рекурсия идёт через обнуляемые нетерминалы, например `S>BBB|C`, `A>S|Sb|bBA|ba`, `B>`,
`C>BABC|BB|SB|aaSb`: здесь лимит исчерпывается уже на `ba` (2 символа), потому что магазин
до высоты отсечения 5 заполняется всевозможными комбинациями символов, выводящих ε. Неверного
ответа при этом нет — только «не установлена».

### Что выводится при отказе

Если ни одна ветвь не дошла до (s0, ε, ε), печатается ветвь, прочитавшая больше всего символов, и
что ветви, дошедшие до этой позиции, ожидали увидеть следующим (FIRST от содержимого магазина: с каких
терминалов может начинаться то, что в нём лежит). Если ожидаемый символ на входе есть, но ветвь всё
равно погибла, программа поясняет, что дело не в этом символе, а в остатке входа (его отсекли по длине,
составу или хвосту). Пример — `a+` в грамматике из методички: `a` подходит, но после `a+` нужен ещё
хотя бы один символ.

Для успешного разбора, кроме цепочки конфигураций, печатается и левый вывод, который она моделирует
(в методичке он приведён после примера): после каждой команды (1) сентенциальная форма — это
прочитанная часть входа плюс магазин сверху вниз.

## Структура программы

Один файл `main.cpp` (~650 строк), без классов сверх нужного:

| Часть | Что делает |
| --- | --- |
| `struct Grammar`, `readGrammar` | разбор файла: `>`/`\|`/`~`, проверки, VN и VT в порядке появления, I — левая часть первого правила |
| `class PushdownAutomaton` | автомат, построенный по грамматике |
| — конструктор | нумерует команды (1), (2), (3); считает minLen и FIRST |
| — `printDefinition` | печатает G, множества S, P, Z, F, команды (1)–(3), начальную конфигурацию (4), minLen |
| — `enter` | шаг в новую конфигурацию: пять отсечений, запись на ветвь, запоминание самой длинной ветви для диагностики |
| — `search` | цикл перебора с возвратом: какой переход из вершины ветви пробовать следующим |
| — `minLength`, `terminalsFit`, `tailMatches` | проверки для отсечений 2, 3, 4 |
| — `recognize` | готовит вход (пробелы, `~`), запускает `search`, печатает цепочку конфигураций, левый вывод и заключение |
| `main` | аргументы, чтение грамматики, цикл ввода цепочек до пустой строки/EOF |

Магазин хранится строкой: дно слева (символ `\x01` = h0), вершина — последний символ, так что
магазин печатается ровно в той записи, что в методичке (`h0T+E`). Конфигурация — пара (позиция во
входе, магазин): состояние у автомата одно, s0, хранить его незачем.

## Вывод

Построенный по грамматике МП-автомат с одним состоянием моделирует левый вывод: команды (1)
раскрывают нетерминал в вершине, команды (2) сверяют полученные терминалы со входом. Недетерминизм
снимается перебором с возвратом; чтобы перебор заканчивался и на леворекурсивных грамматиках, ветви
отсекаются по необходимым условиям (длина, состав, хвост, высота магазина, повтор конфигурации), и
ни одно из них не может выбросить успешную ветвь. Программа печатает всё, что требуется на «отлично»,
а на грамматике из методички выдаёт ту же цепочку конфигураций, что и пример в методичке.
